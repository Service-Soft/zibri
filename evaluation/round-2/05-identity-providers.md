## CRITICAL

### I1. `BaseGoogleAuthenticator` refuses every real Google sign-in, and `BaseMicrosoftAuthenticator` every Entra sign-in of an app registration that does not add `auth_time` — CRITICAL
*Filed 2026-10-21.*

`BaseOidcAuthenticator.resolveSignIn` exchanges the code and then refuses the sign-in as `invalid` when the ID token carries no `auth_time` (`packages/zibri/src/auth/authenticators/oidc/base-oidc.authenticator.ts:202-205`: `if (claims?.auth_time == undefined || ...) throw new FederatedSignInError(FederatedSignInFailure.INVALID, ...)`). The comment at line 210 says why: "the provider was asked for it with max_age, and the check above refuses a token without it", and `getAuthorizationParameters` always sends `max_age` (lines 178-186). The design (03 §H2) rests on OIDC Core 3.1.2.1, which says a provider that receives `max_age` MUST include `auth_time`.

Google does not. Its discovery document lists `claims_supported` as `aud, email, email_verified, exp, family_name, given_name, iat, iss, name, picture, sub` — I fetched `https://accounts.google.com/.well-known/openid-configuration` while writing this, and it has no `auth_time`; Google's authorization endpoint documents no `max_age` either. So every sign-in through `BaseGoogleAuthenticator` (`oidc/providers/base-google.authenticator.ts`), which overrides neither `resolveSignIn` nor the parameters, lands on `errorUrl?error=invalid`, and the audit trail records a refused login. The built-in provider that heads the docs page (`docs/sign-in-through-a-provider.md:60-86`) does not work against the provider it is named after.

Microsoft Entra ID lists `auth_time` in `claims_supported`, but as an *optional claim*: a v2.0 ID token carries it only when the app registration adds `auth_time` under optional claims, and Entra does not document `max_age`. `BaseMicrosoftAuthenticator` (`oidc/providers/base-microsoft.authenticator.ts`) says nothing about that, and neither does the docs table at `sign-in-through-a-provider.md:404-416`. With the default registration the outcome is the same `invalid` on every sign-in. Apple sends `auth_time`, Keycloak does too (its container test passed), so those two are fine. A second consequence for a provider that sends `auth_time` but ignores `max_age`: `exchangeCode` passes `maxAge` to openid-client (`base-oidc.authenticator.ts:197-201`), which throws when `auth_time` is older than `maxAuthenticationAgeInMs`; the OIDC path has no equivalent of SAML's "start again with ForceAuthn" (`base-saml.authenticator.ts:622-626`), so a user with an older provider session is refused as `invalid` with nothing telling them to sign in at the provider again.

Why nothing caught it: `startFakeOAuthProvider` always writes `auth_time` (`packages/testing/src/fake-oauth-provider/fake-oauth-provider.model.ts:240,260,450`), and no test runs against Google or Entra. 03 §H17 recorded exactly this risk for Apple ("not verified against Apple itself; in particular that its ID tokens carry `auth_time`, without which every sign-in is refused as invalid") and §H15 "not verified against GitHub itself"; the same sentence was never written for Google and Microsoft, which are the two a large company would use first. This is a shipped integration that cannot work, found by reading one public document, which is why it is CRITICAL rather than MAJOR.

Fix direction: a provider has to be able to say whether it answers `max_age`/`auth_time`. `BaseOAuth2Authenticator` already has the honest fallback (`authenticatedAt: new Date(0)`, "never counts as a recent login", `oauth2/base-oauth2.authenticator.ts:135-140`); `BaseOidcAuthenticator` needs the same for a provider without `auth_time`, chosen per provider (required, as CODE_STYLE asks for a security choice with two legitimate answers), with `BaseGoogleAuthenticator` and `BaseMicrosoftAuthenticator` fixing it. For Microsoft the alternative is to document the optional claim and keep the strict check. Either way the sign-in with a stale `auth_time` should restart with `prompt=login` the way SAML restarts with `ForceAuthn`, not fail.

**Verify:** Give `startFakeOAuthProvider` an `issuesAuthTime: false` option (as it has `issuesIdToken: false`) and, in `base-google.authenticator.test.ts` on the in-memory data source through `startTestServer`, sign a linked user in through `BaseGoogleAuthenticator` against it: red today with `error=invalid` on the error url. For the real providers, the user runs one manual sign-in against a Google OAuth client and against an Entra app registration without optional claims; both end on `errorUrl?error=invalid`.

> **Closed 2026-10-21, the first way the finding offered.** `BaseOidcAuthenticator` has a required
> `authenticationTime` (`OidcAuthenticationTime`, `'auth_time' | 'none'`): `'auth_time'` sends
> `max_age` and requires the claim, `'none'` sends no `max_age`, requires nothing and records the
> login time as the epoch, the way `BaseOAuth2Authenticator` already did. Google is `'none'`,
> Keycloak and Apple `'auth_time'`, and `BaseMicrosoftAuthenticator` leaves it abstract with the
> optional claim named in its JSDoc and a docs section, since both answers are legitimate there. The
> age is judged by the authenticator rather than by openid-client's `maxAge` check: an `auth_time`
> older than allowed now starts the sign-in again with the reauthentication prompt, the way SAML
> restarts with `ForceAuthn`, and a provider that ignores the prompt is refused on the second
> answer. `resolveSignIn` may answer `FederatedReauthentication` for that. The fake provider got
> `issuesAuthTime`; the Google suite runs against it and holds the sign-in, the absent `max_age`
> and the epoch login time (red first: `error=invalid`), the OIDC suite the restart and the refusal
> after an ignored prompt, plus a `@ts-expect-error` on a subclass that says nothing. The manual
> sign-ins against Google and Entra stay with the user.

## MAJOR

### I2. An OIDC or SAML sign-in hands the application nothing but an email and a name: no claims, no groups, no hook on a later sign-in — MAJOR
*Filed 2026-10-21.*

What a provider proves about the user is reduced to `FederatedProfile` (`federated/federated-profile.model.ts`: `email`, `emailVerified`, `name`, `givenName`, `familyName`) by `resolveProfile` (`oidc/base-oidc.authenticator.ts:156-168`, `saml/base-saml.authenticator.ts:404-412`), and that is all the registration gets (`FederatedRegistration`, `federated/federated-registration.model.ts`). On every later sign-in of a known identity, `completeSignIn` looks the identity up, writes a handover code and returns (`federated/base-federated.authenticator.ts:462-482`); the application is never called. Compare `BaseLdapAuthenticator`, which has a required `resolveSignIn(entry, user, transaction)` on every sign-in and every refresh, with the entry's attributes and groups (`ldap/base-ldap.authenticator.ts:187-198, 278-284`), and SCIM, which has `resolveGroupMembership`.

For an enterprise the consequence is that the two protocols its identity provider actually speaks cannot drive authorization. Entra app roles and `groups` claims, Keycloak realm/client roles, Okta `groups`, ADFS group attributes in a SAML assertion: none of them reaches the application, so roles cannot follow the directory the way the LDAP page shows (`docs/sign-in-through-a-directory.md:138-156`), and someone removed from a group keeps their role in the application until an administrator notices. The same closed type blocks every other claim an identity architect checks: Google's `hd` (hosted domain) to admit only `@corp.com` accounts, Entra's `tid`, `amr`/`acr` (I5), Entra's `oid` — which is also the only stable key for joining an OIDC sign-in to a SCIM-provisioned user, since SCIM's `externalId` is the object id and the ID token's `sub` is pairwise (I3). With both features configured as the docs show, a provisioned user's first sign-in arrives at the registration with no way to find their provisioned account except the unverified email the docs warn about (`sign-in-through-a-provider.md:231`).

What an application can do today is override the protected `resolveSignIn` (OIDC) and read `tokens.claims()` itself, or override `resolveProfile` and smuggle values into `name`; neither is a hook, neither runs for a known identity with the user in hand, and neither is in the docs. I checked whether this was decided: §H2 lists a first sign-in as "the application's business" and gives it a ticket, §H4's second round added the LDAP hook precisely because "someone taken out of a group loses its role at their next sign-in", and nothing in 03 or 11 records why OIDC and SAML were left without one.

Fix direction: give `FederatedProviderIdentity`/`FederatedRegistration` a `claims: Record<string, unknown>` (the verified ID-token claims, the SAML attributes) and add the LDAP-shaped pair to `BaseFederatedAuthenticator` — a required `resolveSignIn(identity, user, transaction)` on a known identity, called inside the login's transaction — so roles can be kept in step and a sign-in can be refused on a claim. `RefreshResolvingAuthenticatorInterface` cannot apply (a provider is not asked at refresh), which is worth saying in the docs.

**Verify:** In `base-oidc.authenticator.test.ts` (in memory, `startTestServer`, fake provider issuing a `groups` claim), sign a linked user in whose provider groups changed and assert the user's roles changed with them; and assert the registration of a new identity can read the `groups`/`hd` claim. Both have no API to call today.

> **Closed 2026-10-22.** `FederatedProviderIdentity` and `FederatedRegistration` carry `claims: Record<string, unknown>`: the verified ID-token claims for OpenID Connect, the assertion's attributes and NameID for SAML (the node-saml profile without its functions), and whatever `resolveIdentity` answers as `claims` for plain OAuth2 (optional there, `{}` when left out, so GitHub and the docs' forge example are unchanged). The registration ticket and the handover code keep them as an `unknown` column, so the hook runs where the finding asked for it: `BaseFederatedAuthenticator.resolveSignInUser(claims, user, transaction)` is called in `authenticate` on the handover path, inside the login's transaction, with the user the identity is linked to, and answers the user the login is for. Named `resolveSignInUser` rather than the directory's `resolveSignIn`, which `BaseOAuthAuthenticator` already uses for proving the sign-in. Not abstract, deliberately: a Google sign-in has nothing to sync, and the default answers the user as they are. Not called on the ticket path (the registration just made the user from the same claims) and not on a refresh (the provider is not asked), which the docs say. Found on the way: a refusal thrown past the callback - the hook's, or `AccountDeactivatedError`/`AccountLockedError` - landed on the error url as `expired`; `FederatedSignInFailure.REFUSED` now names it (`toFailureCode` maps every `ForbiddenError` to it). Tests: `base-oidc.authenticator.claims.test.ts` (in memory, cookies, fake provider with `identity.claims`): roles follow the `groups` claim across two sign-ins, a blocked group lands on `errorUrl?error=refused` without a session, and the registration reads `sub`, `email`, `groups` and `hd`. The fake provider's `FakeOAuthIdentity.claims` go into its ID tokens and access tokens. None of the cases compiled before the change.

### I3. `ProviderTokenAuthStrategy` cannot work with Entra ID across app registrations: identities are keyed on the pairwise `sub`, and the subject claim is not selectable — MAJOR
*Filed 2026-10-21.*

An identity is stored as `(issuer, subject)` with `subject = claims.sub` of the sign-in's ID token (`oidc/base-oidc.authenticator.ts:206-213`, `federated/federated-identity.model.ts`), and a bearer token of the provider is matched to it by `verified.payload.sub` (`base-oidc.authenticator.ts:130-133`). Microsoft documents `sub` as a pairwise identifier, unique per application id: the same person signing into two client ids gets two different `sub` values, and an access token issued for the API resource carries yet another. So a mobile app registration obtaining a token for the API (the exact scenario `docs/provider-tokens.md:2` names, "such as Keycloak, Microsoft Entra ID or Auth0") presents a `sub` that no sign-in through the web client ever linked. Every such request is refused with 401 as "an identity linked to nobody" (`provider-tokens.md:67`).

03 §H14 saw this coming — "Entra's per-application `sub` may differ between a sign-in's ID token and an api's access token, which would leave such a token unlinked; not verified against Entra" — and closed anyway. It is not an unverified corner; it is Microsoft's documented contract, and it makes the strategy unusable with the provider the docs advertise it for unless web client, mobile client and API are one app registration, which Microsoft's own guidance discourages. The stable key is `oid` (plus `tid`), and there is no member or hook to choose it: `subject` is read from `sub` in both places with no override point short of replacing `resolveSignIn` and `findProviderToken` together.

Fix direction: a `subjectClaim` (default `sub`) on `BaseOidcAuthenticator`, read in both `resolveSignIn` and `findProviderToken`, set to `oid` by `BaseMicrosoftAuthenticator`; the identity's `issuer` would then also have to be the tenant issuer for both token kinds, which it is for a single-tenant registration.

**Verify:** In `provider-token.auth-strategy.test.ts` (in memory), have the fake provider issue an ID token with `sub: 'pairwise-web'` and `oid: 'stable'` for the sign-in and an access token with `sub: 'pairwise-mobile'` and the same `oid`; a request with the access token must act as the linked user. Red today. The container case `takes the access token a mobile app holds from Keycloak` (`base-keycloak.authenticator.test.ts:573`) passes only because Keycloak's `sub` is global.

> **Closed 2026-10-22.** `BaseOidcAuthenticator.subjectClaim` (`'sub'` by default) is the claim an identity is stored and looked up by, in `resolveSignIn` (a token without it is `invalid`) and in `findProviderToken` (a token without it names nobody). `BaseMicrosoftAuthenticator` sets `'oid'`. The issuer stays the tenant issuer, which both token kinds of a single-tenant registration carry. Breaking for identities linked under 2.x by `sub`: the upgrade guide says to rewrite their `subject` to the object id, or to set `subjectClaim` back to `sub`. Tests: the sign-in half in `base-oidc.authenticator.claims.test.ts` (an identity registered under `web-…`/`oid` signs in again under `other-…`/the same `oid` as the same user; a token without the claim lands on `error=invalid`), the token half in `provider-token.auth-strategy.test.ts` (an access token with `sub: pairwise-mobile` and the linked `oid` acts as the user; the same value as `sub` with no `oid` is refused) - the token case was 401 before the change.

### I4. Nothing propagates a logout for OpenID Connect: no RP-initiated logout, no back-channel, no front-channel — MAJOR
*Filed 2026-10-21.*

`createLogoutUrl`, `readProviderLogout` and `resolveSoapLogout` on `BaseFederatedAuthenticator` default to "cannot be told" / 404 (`federated/base-federated.authenticator.ts:626-663`), `BaseSamlAuthenticator` overrides all three, and `BaseOidcAuthenticator` and `BaseOAuthAuthenticator` override none. So for every OIDC provider: `POST /auth/logout` never answers a `providerLogoutUrl` (the `end_session_endpoint` every enterprise provider publishes is never read), the provider's session outlives the application's, and the next `authorize` silently signs the same person in again; and a logout at the provider — a help-desk "sign out everywhere", a Conditional Access revocation, an Okta session kill — reaches the application never, since there is no route for OpenID Connect Back-Channel Logout 1.0 or Front-Channel Logout, which Entra, Okta, Keycloak, Auth0 and PingFederate all implement.

This was listed in §H2 as "Out of H2: logging out at the provider (by redirect or by its back-channel call)" and was not filed afterwards; 11 does not carry it. The SAML half was built in full (§H3, §H23: redirect, POST and SOAP logout, both directions, sessions ended precisely by `endFederatedLogins`), so the model exists — `FederatedSession` already keeps `subjectKey`/`sessionKey` (`base-federated.authenticator.ts:770-785`), and an OIDC `sid` claim fits `sessionKey` exactly. An identity architect with a SIEM counts "terminate all sessions of a compromised account at the IdP" among the first controls to test; today it ends nothing here.

Fix direction: implement the three hooks on `BaseOidcAuthenticator` — `end_session_endpoint` with `id_token_hint`/`post_logout_redirect_uri` for `createLogoutUrl`, a `POST /federated/:provider/backchannel-logout` taking a logout token (verified with the provider's keys, `events` claim, `sid`/`sub`, `jti` single use), and `readProviderLogout` for the front-channel `iss`/`sid` query — and keep the ID token's `sid` as the session key at sign-in.

**Verify:** In `base-oidc.authenticator.test.ts` (in memory), extend the fake provider to publish `end_session_endpoint` and to send a back-channel logout token; assert `POST /auth/logout` answers a `providerLogoutUrl`, and that a logout token for the session ends exactly that login (both strategies) as the SAML suite asserts for SLO. Red today: the route does not exist.

> **Closed 2026-10-22.** All three directions on `BaseOidcAuthenticator`, on the SAML model. At sign-in the ID token's `sid` is the session id and the ID token itself is what the login keeps to end the session with (`FederatedSignIn.session`, which `OAuthProviderSignIn` now carries). OIDC session keys hash the session by `[issuer, sid]` alone - a provider's logout names the session without the person - so `FederatedSessionMatch.subjectKey` became optional (`toWhere` filters by whichever key is given, and refuses a match with neither). (1) `createLogoutUrl`: the published `end_session_endpoint` with `id_token_hint`, `client_id` and `post_logout_redirect_uri` = the logout route, which the provider sends the browser back to and which lands on `signedOutUrl`. (2) A new `resolveBackChannelLogout(token)` hook on `BaseFederatedAuthenticator` (404 by default, on the interface) behind `POST /federated/:provider/logout/back-channel`, taking the posted `logout_token`: verified against the provider's keys (`JwtUtilities.verifyLogoutToken`: issuer, audience = client id, allowed algorithms, `iat` within 10 minutes, `jti`, `events`), the back-channel event required, a `nonce` refused, `sid` and/or `sub` required, and the `jti` spent through a lease for the token's lifetime so a replay against another replica is refused too. (3) `readProviderLogout` reads the front-channel `iss`/`sid` query into the session, and treats a query without either as the browser coming back from (1). The OIDC authenticator declares the `logout` (GET) and `logout/back-channel` routes, so the url check at boot covers them. Microsoft's `oid` subjects: a logout token's `sub` is pairwise, so for Entra only the session path matches, which is the one it uses (front-channel). Tests: `base-oidc.authenticator.logout.test.ts` (in memory, cookies, the fake provider publishing an end session endpoint and signing logout tokens): the logout answers the end session url with the ID token, the client and the way back, and the browser lands on the signed-out page; a token naming the session ends exactly that login, refreshed or not; one naming the user ends every login of theirs and nobody else's; a token another provider signed, one without the event, one with a nonce, one naming nobody and a replay are refused; a front-channel logout ends the session's login, and one naming another provider or no session is refused. None of the cases compiled before the change, and the SAML suite still passes on the shared model.

### I5. The provider's MFA is invisible, so every `@Auth.require2fa` route asks an Entra-or-Okta-authenticated user for a second factor again — MAJOR
*Filed 2026-10-21.*

`require2fa` is satisfied by a second factor enrolled in the application or by a recent login (03 §H13); a sign-in through a provider counts as a login at `auth_time` and nothing else. The `amr` and `acr` claims of the ID token are not read (`resolveProfile`, `base-oidc.authenticator.ts:156-168`), SAML's `AuthnContextClassRef` is not read and `disableRequestedAuthnContext: true` sends no request for one (`base-saml.authenticator.ts:736-738`), and `acr_values` is never sent. So a company whose identity provider enforces MFA (Conditional Access, Okta sign-on policies, Keycloak step-up) gets no credit for it: the user who just passed Entra's MFA must enrol TOTP, SMS or a passkey in the application to pass a `require2fa` route, and `'onlyAsFallback'` only lets them through on a login that is at most five minutes old. Two MFA enrolments per application is what identity teams explicitly try to avoid, and is a standard reason for refusing an application in an SSO review.

§H2 listed "counting the provider's MFA (`amr`) as the second factor" as out of scope; nothing re-filed it and 11 does not carry it. A deliberate decision not to trust the provider's MFA would be defensible for a consumer provider and is the wrong default for a company's own identity provider, which is the trusted party for the password already.

Fix direction: keep the claims on the login (`amr`/`acr`/`AuthnContextClassRef` on `Authentication` and the refresh row, as `authenticatedAt` is kept) and let `require2fa` accept a configured set of `acr`/`amr` values as a second factor, with `acr_values`/`RequestedAuthnContext` sent on `reauthenticate` so a step-up can be requested from the provider instead of a code.

**Verify:** In `auth-sessions-and-2fa.evaluation.test.ts` style (in memory): a fake provider issuing `amr: ['mfa']`; a `require2fa` route configured to accept it passes for that login and refuses a login with `amr: ['pwd']`. No option to configure exists today.

> **Closed 2026-10-22.** `ProviderAuthentication { methods, contextClass }` - the `amr` values and the `acr` of an ID token, the AuthnContextClassRef of a SAML assertion (read off the parsed authentication statement; node-saml parses text as `{ _ }`, which `findText` unwraps) - travels on `FederatedProviderIdentity`, the handover code and the registration ticket, on to `Authentication.providerAuthentication`, and is kept by the login as `authenticatedAt` is: an `unknown` column on `JwtRefreshToken` and `CookieAuthRefreshSession` carried through every rotation, and the `amr`/`acr` claims of the application's own access token. A new optional `resolveProviderAuthentication(context)` on `AuthStrategyInterface` answers it for the current request (jwt from the token, cookies from the refresh session, `ProviderTokenAuthStrategy` from the provider's token itself); a strategy without it never counts. `@Auth.require2fa({ providerFactors: { methods, contextClasses } })` lets a login through that reported one of them, with `ZIBRI_DI_TOKENS.REQUIRE_2FA_PROVIDER_FACTORS` (`false`) as the application-wide default - none by default, since which of a provider's factors to trust is the application's to say, as the finding itself allows. Checked after the lock (a locked factor is not stood in for, as a recent login is not) and before the reauth fallback. The step-up request: `acrValues` on `BaseOidcAuthenticator` goes out as `acr_values`, `requestedAuthnContext` on `BaseSamlAuthenticator` as the RequestedAuthnContext (and node-saml's password-only default stays off), so a login that does not count is sent back with `reauthenticate` and the provider asks for the factor. Tests: `base-oidc.authenticator.claims.test.ts` (cookies: a login with `amr: ['pwd','mfa']` passes the route counting the method, not the one counting a class or the one that says nothing, and still passes after a rotation; `acr` passes the class route; `['pwd']` and nothing are refused; `acr_values` goes to the provider; jwts: the factor rides the ticket into a jwt login handed over by code, and its refresh), `provider-token.auth-strategy.test.ts` (an access token's own `amr` counts), `base-saml.authenticator.test.ts` (the assertion's class counts across a rotation, a password alone does not; the step-up authenticator's request names the class, the plain one's names none). The fake providers gained `identity.claims` (OAuth) and `identity.authnContextClassRef` plus `requests[].requestedAuthnContext` (SAML). None of the cases compiled before the change.

## MINOR

### I6. An outage of the provider's token endpoint is reported to the user and the audit trail as a forged answer — MINOR
*Filed 2026-10-21.*

`exchangeCode` maps *every* error from `authorizationCodeGrant` to `FederatedSignInFailure.INVALID` (`oauth/base-oauth.authenticator.ts:304-316`), which the error url shows as "The provider's answer could not be verified" (`docs/sign-in-through-a-provider.md:189`). Only a discovery failure is `PROVIDER_ERROR` (lines 297-303), and only the OAuth2 user-info path distinguishes a refusal from "the provider's api not answering" (`oauth2/base-oauth2.authenticator.ts:121-130`). A timeout (the http client's 5 s `defaultTimeoutMs`), a 502 from the token endpoint, or a TLS failure therefore reads exactly like a wrong `state`, a tampered code or a failed signature.

The consequence is in the trail, not only on the user's screen. `FederatedSignInError` extends `UnauthorizedError` (`federated/federated-sign-in.error.ts:22`), so `FederatedRouteUtilities.toFailure` treats it as a refusal: an audit row `auth.login` / `failure` with reason `invalid`, and no error log (`federated/federated-route.utilities.ts:308-320`) — the design note at line 302 says a fault "is thrown on rather than turned into a redirect ... folding it in would make an outage look like a failed sign-in", which is exactly what happens here. A SIEM rule on a burst of invalid federated callbacks fires on a Google incident, and an on-call engineer sees nothing in the logs.

Fix direction: classify by cause — openid-client's `ResponseBodyError` with an OAuth2 error code is `INVALID`/`CANCELLED`; anything else (network, timeout, non-2xx without an OAuth2 body, `WWW-Authenticate` challenge) is `PROVIDER_ERROR` and logged as a warning with the cause, as `revokeAtProvider` already does (`base-oauth.authenticator.ts:578-585`).

**Verify:** In `base-oidc.authenticator.test.ts`, stop the fake provider's token endpoint (or make it answer 503) between authorize and callback; assert the error url carries `provider_error` and a warning was logged. Red today (`invalid`, nothing logged).

### I7. One issuer per authenticator: a multi-tenant Entra registration (`common`/`organizations`) cannot sign anyone in — MINOR
*Filed 2026-10-21.*

`BaseMicrosoftAuthenticator.issuer` is `https://login.microsoftonline.com/${tenantId}/v2.0` (`oidc/providers/base-microsoft.authenticator.ts:26-28`) and `createConfiguration` discovers exactly that issuer (`base-oidc.authenticator.ts:170-176`). Entra's multi-tenant endpoints publish an issuer template with `{tenantid}` and sign tokens with the real tenant's issuer, which openid-client refuses as a mismatch. An application that wants any Microsoft work account — or a group with several Entra tenants after acquisitions, where the user should not have to pick the tenant first — has no way through; one authenticator per known tenant is the only option, each under its own `name` and callback url. §H2 listed "a multi-tenant issuer such as Entra's `common`" as out of scope and §H20 (open) covers a tenant bringing its own provider as data, which is a different feature. Fix direction: an `allowedIssuers`/issuer-pattern on `BaseOidcAuthenticator` with per-tenant discovery keyed by the ID token's `tid`, validated after the exchange.

**Verify:** A fake provider whose discovery issuer carries a placeholder and whose ID token names a concrete tenant issuer; a sign-in through an authenticator configured for the placeholder issuer should succeed when the concrete issuer is allowed. Red today at discovery.

### I8. Provider metadata is read lazily, cached for the life of the process and never checked at boot — MINOR
*Filed 2026-10-21.*

`BaseOAuthAuthenticator.init` loads the `openid-client` module and nothing else (`oauth/base-oauth.authenticator.ts:107-114`); discovery happens on the first sign-in (`resolveConfiguration`, lines 323-330) and the `Configuration` promise is then kept until the process ends. A wrong `issuer`, an unreachable provider or a `private_key_jwt` key the provider does not know is found by the first user, not by the deployment; the framework's own rule elsewhere is "a missing package stops the boot rather than the first login" (§H12). And endpoints the provider moves (Keycloak hostname change, an Okta custom authorization server, a Keycloak `token_endpoint` rewrite) are picked up only by a restart, while the SAML side re-reads its metadata daily (`base-saml.authenticator.ts:91, 782-814`). The provider's JWKS is handled by jose/openid-client with their own refresh on an unknown `kid`, so key rotation is fine; it is the discovery document that is frozen.

Fix direction: a boot-time discovery in `init` (with a documented opt-out for environments where the provider is unreachable at boot) and a `METADATA_MAX_AGE`-style re-read, sharing the SAML authenticator's "use the last good one while the provider is unreachable" shape.

**Verify:** In `base-oidc.authenticator.test.ts`, boot with a fake provider whose discovery answers 500: today the application starts and the first sign-in lands on `provider_error`. And with a provider whose `token_endpoint` changes after the first sign-in: the second exchange still goes to the old url.

### I9. The protocol constants an enterprise would tune are hardcoded — MINOR, from `after-all-findings-fixed.md` item 13
*Filed 2026-10-21.*

From the user's own list. The ones in this area, each a literal rather than an option or a member: SAML accepted clock skew of one minute (`saml/base-saml.authenticator.ts:86`, passed at 749) and metadata max age of one day (line 91); the provider access token refresh margin of 60 s (`oauth/base-oauth.authenticator.ts:42`) and the refresh lease of 30 s / 15 s acquire (line 173) — a provider whose token endpoint takes longer than 30 s lets a second refresh start under an expired lease, which is the race the lease is there for; the first-sign-in lease of 30 s in LDAP (`ldap/base-ldap.authenticator.ts:40`); the client assertion lifetime of one hour (`authorization-server/authorization-server.service.ts:71`, modified in the working tree); the `DisabledLdapEntriesCronJob` page size and interval; the federated cleanup every hour (`federated/federated-cleanup.cron-job.ts:18`). **Verify:** A unit test asserting that a subclass can set `acceptedClockSkewMs` and that an assertion two minutes ahead of the application clock is accepted under it; today there is no member to set.

### I10. LDAP opens a fresh TLS connection and bind for every sign-in, every refresh and every cookie renewal, and fails over sequentially — MINOR
*Filed 2026-10-21.*

`resolveServiceConnection` creates a new `ldapts` client, connects (StartTLS or ldaps), binds as the service account and is unbound at the end of each `resolveEntry` and `resolveRefreshUser` (`ldap/base-ldap.authenticator.ts:425-448, 253-289, 543-573`). §H22 made `resolveRefreshUser` run on every jwt refresh, every cookie refresh route and every cookie session renewing itself inside a request, so with 10k linked users and a 15-minute access token the directory sees a TLS handshake plus bind plus search roughly every 90 ms, all day, with no pool. A slow directory is also serialised: with `urls` of three servers and `connectTimeout` of 10 s, a network partition makes a single refresh wait up to 30 s (`timeoutInMs`, line 156; the loop at 547-568 tries the next server only after the previous one failed) before the 500 the docs promise. And `attributes: ['*']` (line 139) reads every attribute of the account on each of those round trips, which on Active Directory includes `thumbnailPhoto` and `jpegPhoto`.

Deliberate in part — the one-at-a-time failover is commented at line 550, and a fresh connection per bind avoids the known pitfalls of rebinding on a pooled connection — but the per-refresh directory round trip was added in §H22 without revisiting the cost. Fix direction: a small pool of service-account connections (bind once, search many; bind-as-user on a separate short-lived connection), a `Promise.any`-style race for the first reachable server, and a `refreshCheckIntervalInMs` so the directory is asked at most once per user per interval rather than per refresh. Separately worth checking: `findEntry` asks with `sizeLimit: 2` (line 468); when three or more entries share the name a real server answers `sizeLimitExceeded` (result code 4), which `ldapts` raises as `SizeLimitExceededError` — then the sign-in is a 500, not the 401 the docs promise. The fake directory does not reproduce this.

**Verify:** Against the fake directory (in memory), count connections opened for 100 refreshes of one user (today 100), and time a refresh with two unreachable servers listed first (today ≥ 20 s). For the size limit, the 389 heavy suite with three entries sharing a `uid` and `sizeLimit: 2`.

### I11. `Bearer` and the api key header are matched case-sensitively — MINOR
*Filed 2026-10-21.*

`AuthorizationHeaderUtilities.findToken` takes only `Bearer` and `DPoP` spelled exactly so (`strategies/authorization-header.utilities.ts:26`), and `ApiKeyAuthStrategy.findBearerKey` the same (`strategies/api-key/api-key.auth-strategy.ts:166`, modified in the working tree); RFC 9110 §11.1 makes the scheme case-insensitive, and `bearer` from a hand-written client or a load balancer that normalises headers is refused as no credential at all, which on a guarded route is a bare 401 with nothing explaining why. `ApiKeyAuthStrategy` also reads `context.request.headers?.[this.header]` with the injected header name as given (`api-key.auth-strategy.ts:61, 139`); node lowercases incoming header names, so an application that provides `ZIBRI_DI_TOKENS.API_KEY_HEADER` as `X-Api-Key` silently never sees a key, while `BaseClientCertificateAuthStrategy` lowercases its header (`client-certificate/base-client-certificate.auth-strategy.ts:193`). The OpenAPI scheme would still advertise the configured spelling. **Verify:** two in-memory cases in `api-key.auth-strategy.test.ts`: `authorization: bearer zibri_…` is taken, and a strategy built with `X-Api-Key` takes the key.
