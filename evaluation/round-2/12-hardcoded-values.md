# 12 — Hardcoded values

*Filed 2026-10-30.* The user asked for a sweep over values the framework hardcodes that an application
might want to set, password length being the example. A value already settable through a DI token, an
option model, an overridable property of a provider or `CronService.changeCron` is not filed. Every row
was re-read against the code, its comments and docs/ before filing; the ones dropped for a recorded
reason are listed at the end.

IDs are this chapter's own: `12 §A1` is not `04 §A1`. All open rows are MINOR: an application can work
around each of them by overriding a provider, at the cost of copying framework code.

## Dropped, with the reason on record

- The mail rate limiter counting per instance: 06 §Q7, email.md shows the shared one.
- The queue retry backoff: it ends with the row's attempts (`queue.utilities.ts:212`).
- The 2FA failure delay doubling without a ceiling: on purpose, `two-factor.service.ts:331`.
- The `x-tenant-id` header: `TenantService.resolveTenant` is overridable, tenancy.md.
- No cap on `Retry-After` in the http client: the server's value is obeyed on purpose, `http-client.ts:943`.
- `Referrer-Policy`: app-settings.md lists it as fixed, and it is the browsers' default.
- The 12 h before a staged backup file counts as abandoned: counted from its last write, so a backup still writing keeps it, `backup-staging-cleanup.cron-job.ts:12`.

From O3, checked 2026-10-31:

- Pacing behind a wake-up, so the interval is only the fallback when a notification is lost: lease acquiring (100 ms, 1 s, `lease.service.ts`), remote thread jobs (100 ms, 5 s, `multithreading.service.ts`), the first poll backoff (1 s, `poll-pacing.model.ts`).
- Retry pacing of an internal operation that succeeds on its own once the other side is back: postgres notification reconnect (1 s), schema lock retry (100 ms), valkey lock wait and retry (500 ms, 100 ms), valkey resubscribe (1 s) and subscribe timeout (5 s), audit write retry (5 s), backup resource wait (1 min, retried by the queue).
- The valkey rate limiter lock (5 s TTL, 5 ms × 400 attempts): it guards one counter update for a moment, and a setting would only tune contention on a single key.
- Attempts against a conflict that only repeats under a defect: chain writes (5), valkey key changes (3), spanning restore (3).
- Batch and page sizes, which change round trips and nothing an application sees: `STREAM_BATCH_SIZE` 500, chain pages 1000, encryption report pages 200, valkey backup walk 250, cache eviction chunks 50, thread job candidates 10, backup encryption chunks 64 KiB.
- `UNBOUNDED_FIND_ALL_LIMIT` (10000): a read that needs more says `limit: 'all'`, upgrading-to-3.md.
- The websocket answers margin (1 s), the LDAP first login lease (30 s), the valkey clock reading age (1 min), event loop utilization sampling (100 ms), staging follow poll (50 ms): an order of magnitude over what they wait for, or a measurement's resolution.
- SFTP keepalive (15 s × 3): it ends a dead connection within a minute, which is what it is for; a working one is unaffected.
- The log flush at shutdown (5 s): inside `shutdownTimeoutInMs`, which is settable.
- `LOGIN_USER_AGENT_MAX_LENGTH` (512) and `PASSWORD_MAX_LENGTH` (1024): storage and hashing caps above anything legitimate; the policy's `maxLength` is the setting.
- `MAX_TIMER_DELAY_IN_MS`, `DAY_IN_MS`: facts, not tuning. The webpack restart stop timeout (10 s): development only.
