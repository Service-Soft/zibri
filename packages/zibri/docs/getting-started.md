# Getting started
A new project is generated by `zi new`, the command line tool of Zibri. It sets up an application
that builds, tests and runs as it stands, with its configuration read from the environment.

## Requirements
Zibri runs on Node 24 and every maintained release after it, on Linux, macOS and Windows. A new Node
release line is tested as soon as it ships.

The template compiler and the extraction of source translations run on the TypeScript your project
installs, 5.9 or 6.

### Build toolchains
Zibri's decorators are TypeScript's `experimentalDecorators` ones, so a project turns that on in its
`tsconfig.json`. Every toolchain that compiles TypeScript implements them.

`emitDecoratorMetadata` is a separate option. It decides how a constructor says what to inject:

| Toolchain | `experimentalDecorators` | `emitDecoratorMetadata` |
|---|---|---|
| `tsc` | supported | supported |
| SWC | `jsc.transform.legacyDecorator` | `jsc.transform.decoratorMetadata` |
| esbuild, and Vite through it | supported | left to the second style below |
| Bun | supported | left to the second style below |

With the metadata, a constructor parameter is resolved from its declared type. Without it, name the
token with `@Inject`. Every toolchain builds that second style:

```ts
// src/services/invoice.service.ts
import { Inject, Injectable } from 'zibri';

@Injectable()
class PdfService {}

@Injectable()
class InvoiceService {
    constructor(private readonly pdf: PdfService) {}
}

@Injectable()
class ReceiptService {
    constructor(@Inject(PdfService) private readonly pdf: PdfService) {}
}
```

`InvoiceService` is resolved from the declared type, which the metadata records. `ReceiptService`
names the token in the code itself.

`zi new` writes a `tsconfig.json` that extends `zibri/tsconfig.application.json`, which has both
options on, so a generated project uses either style. A build that records no metadata names every
token.

A class that declares no constructor of its own is built with the one it inherits. Types are recorded
only for the constructor of a decorated class, so the class declaring that constructor is either
decorated or names its tokens with `@Inject`. In a build that records no metadata, a class whose
parent's constructor takes parameters declares no constructor that takes nothing.

The metadata also checks a number property's declared type against the `format` it names, as the
class is declared. Without the metadata, that check is skipped. The value is checked against the
format as it is stored, either way.

Install the ones you use, such as `npm i socket.io`.

## Installing the CLI
New projects are set up with [zibri-cli](https://www.npmjs.com/package/zibri-cli). Install it with:

```sh
npm i -g zibri-cli
```

## Creating a project

Run

```sh
zi new
```

and answer four questions:

| Question | Answers |
|---|---|
| The name of the project | Any npm package name |
| Whether it gets a continuous integration workflow | `github` or `none` |
| What a route without `@Auth` requires, see [what an undecorated route requires](./auth.md#what-an-undecorated-route-requires) | `isLoggedIn`: a forgotten decorator answers `401`. `public`: a forgotten decorator serves anyone |
| The features it has, see [choosing the features](./project-layout.md#choosing-the-features) | Any of `pages`, `mailingList`, `metricsDashboard` and `logEmail`. None is a JSON API |

All four can be given on the command line instead, as
`zi new <name> <github|none> <isLoggedIn|public> <features|none>`, with the features comma separated.

With `github`, the project gets `.github/workflows/ci.yml`, which installs, builds and tests it on
every pull request and every push to `main`. A checkout has no `.env`, so the workflow copies
`.env.example` and fills each blank secret with a value made for that run.

## Configuring the project

A generated project reads everything that differs between one machine and the next from the
environment: where it runs, the port it listens on, the database it connects to, the secrets it signs
tokens and encrypts columns with, the mail server, and the first administrator it creates.

Two files describe that:

- **`.env.example`** is the checked in list of every variable the project reads, with the secrets
  and `ENVIRONMENT` left blank. It tells a deployment, or the next person to clone the repository,
  what has to be set.
- **`.env`** holds the values, and is git ignored. `zi new` writes one with a freshly generated
  secret for each blank and `ENVIRONMENT=development`, so a new project runs as it stands. In
  development, every mail is logged instead of sent, see
  [saying where the application runs](./architecture.md#saying-where-the-application-runs). In
  production, the project starts once `SMTP_HOST` and `SMTP_PORT` name a mail server.

`src/env.ts` reads them. `requireEnv` is for a variable the project needs, `requireOneOfEnv` for one
that holds one of a few values, and `optionalEnv` for one it runs without.

A deployment that sets its variables directly needs no `.env` at all: the file is loaded when it is
there and skipped when it is not.

## Starting the application
Go into the new project and run `npm start`. [The generated project](./project-layout.md) goes
through every file `zi new` wrote, and how to add or remove a feature later.

The first start records the routes of the project's version in the `versions` folder. Commit it: each
release is checked against what the ones before it recorded, see
[checking a new version against the earlier ones](./versioning.md#checking-a-new-version-against-the-earlier-ones).

## Upgrading a project
Run `zi upgrade` in your project with the cli of the release you upgrade to:

```sh
npm i -g zibri-cli@latest
zi upgrade
```

It installs `zibri` and `zibri-testing` of that release, and every package a new project gets that
yours does not have. Then it brings each file `zi new` generated to what that release generates:

- a file you never changed is replaced.
- a file you changed is merged with what the release changed, the way git merges a branch. Where you
  both changed the same lines, the file has conflict markers for you to resolve.
- a file you deleted stays deleted.

`zibri-scaffold.json` records what was generated, and the merge reads that version back out of your
git history. Commit before you upgrade, and commit the result. A file whose generated version is not in
the history keeps your content, with the release's version beside it as `<file>.zibri-upgrade` to
compare.

`zi upgrade github` or `zi upgrade none` changes which continuous integration workflow the project has.

The build, the jest configuration and the compiler options come from the packages themselves:
`webpack.config.js` calls `resolveWebpackConfiguration` of `zibri/webpack`, `jest.config.mjs` names the
`zibri-testing` preset, and `tsconfig.json` extends `zibri/tsconfig.application.json`. Updating the
packages updates them.
