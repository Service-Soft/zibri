# Changelog

What changed in each release of `zibri`, `zibri-contract`, `zibri-tsx`, `zibri-tsx-compiler`, `zibri-mdx`, `zibri-testing` and `zibri-cli`. They are released together, at one version.

## 3.1.0

### Upgrading from 3.0
- **Take no backup while instances of 3.0 run.** During a rolling deploy, an instance of 3.0 stores the resources of a backup that 3.1 queued the way 3.0 stores every backup, and its retention knows nothing of the backups a backup of 3.1 builds on, nor of the backups of a tenant, so it can delete a backup that another one builds on. A Valkey backup with `backupMode: 'walk'` and a backup of a tenant read the rows as of one moment only from writes of 3.1. Deploy between two scheduled backups, and queue none until every instance runs 3.1. A restore reads a resource that an instance of 3.0 stored where it is. An instance of 3.1 leaves a backup queued in a format it does not write to an instance that writes it, so a later release changing the format needs no pause.
- **Backups taken by 3.1 are in format 2, which 3.0 refuses.** Going back to 3.0, restore one of them with 3.1 first. See [going back to the previous release](https://service-soft.github.io/zibri/operations/incidents/#going-back-to-the-previous-release).
- **The columns 3.1 adds to the entities of the framework take no migration of yours.** With `schemaManagement: 'migrations'`, a Postgres data source adds them to the tables that lack them when it starts, after your migrations ran: `application` of `Log`, `tenantId` of `BackupEntity`, and `stagedSize`, `baseBackupId` and `readCursor` of `BackupResourceEntity`, each nullable. The logs stored before get the `name` of the application. `zi migrate create` leaves these columns out of the migration it writes. Nothing is recorded for them, so an instance of 3.0 starts on the same database, and writes its rows without them. With `schemaManagement: 'synchronize'`, an instance of 3.0 drops them again, as it drops every column its entities do not declare. With `schemaManagement: 'external'`, add them yourself.
- **Run `zi upgrade` for the page of the OpenAPI explorer.** It writes the page into `src/templates/explorer/` and provides it. Without it, `/explorer` sends to the OpenAPI document of the latest version, and the documents are served as before. See [changing the explorer](https://service-soft.github.io/zibri/endpoints/open-api/#changing-the-explorer).
- **Some messages of the framework are worded anew,** such as `A group needs to be a json object.` in place of `A group is a json object.`, so a translation of the old wording no longer applies, and the message is shown as written until it is translated again. The start names every message a locale's file has no translation for. See [localization](https://service-soft.github.io/zibri/templates/localization/).

### Templates
- **The compiler of the templates is the package `zibri-tsx-compiler`**: the webpack loader `zibri-tsx-compiler/webpack`, the jest transform `zibri-tsx-compiler/jest` and the type check. `zibri-tsx` is the runtime a deployment renders with, and names neither the compiler nor TypeScript, so a deployment carries neither, 23 MB of TypeScript among them. Install the compiler as a devDependency, which `zi upgrade` does. `zibri/webpack` and the jest preset of `zibri-testing` use it.
- **State.** `useState` creates a state of a component, and every text and attribute of the markup reading it follows it. A state on the `value` of a field or the `checked` of a checkbox binds both ways. See [keeping the page in step with a state](https://service-soft.github.io/zibri/templates/templating/#keeping-the-page-in-step-with-a-state).
- **Conditions and lists the browser renders.** `cond && <x/>`, `cond ? <a/> : <b/>` and `items.map(item => <li key={...}/>)` reading a state render again when it changes, keyed by row. They can hold components and the `children` of the component: a branch or a row the browser builds later is copied from a template the server renders, and removing one runs the cleanups of its components. See [rendering markup that follows a state](https://service-soft.github.io/zibri/templates/templating/#rendering-markup-that-follows-a-state).
- **`onClient` may return a cleanup**, which runs when the component is removed with its branch or row.
- **`useEffect`** runs code after a state changes, with a cleanup. See [running code after a state changes](https://service-soft.github.io/zibri/templates/templating/#running-code-after-a-state-changes).
- **`useInput` and `useWritableInput`** let a component follow, or write, a state it is handed as a prop or a context. See [handing a state to another component](https://service-soft.github.io/zibri/templates/templating/#handing-a-state-to-another-component).
- **`useRef` and `useRefs`** give client code the elements they are put on. See [reaching an element from client code](https://service-soft.github.io/zibri/templates/templating/#reaching-an-element-from-client-code).
- A mistake only the render can see, such as a required ref on no element, throws in `development` and is logged in `production`. A template rendered before any application is created, such as in a test of the template alone, renders as in `development`, and warns that it throws from 4.0.
- A `let` the markup reads and client code writes compiles with a `ZTSX016` warning, as the markup never follows it. It fails the build from 4.0.
- The build type-checks the templates with the project's `tsconfig.json`, and reports a type error in a template as a warning, naming the file and the line. It fails the build from 4.0. See [templating](https://service-soft.github.io/zibri/templates/templating/).
- A name only the browser has, such as `window` or a `?client` import, read while the server renders compiles with a `ZTSX014` warning, as it throws unless a check keeps it from running on the server. A read under a `typeof` check of the same name has none. It fails the build from 4.0. See [running code in the browser](https://service-soft.github.io/zibri/templates/templating/#running-code-in-the-browser).
- **Pages written in markdown.** A `.md` or `.mdx` template compiles into a page, its default export, with its frontmatter as `frontmatter`. `ZIBRI_DI_TOKENS.MDX_COMPONENTS` names the component each markdown construct renders, the code of a fenced block is highlighted with classes your stylesheet colors, and the build type-checks every page a file imports, its frontmatter against the `MdxFrontmatter` you declare. A markdown file in the templates that nothing imports, such as a README, is left as it is. A page written in markdown is also the text of an email, with the components `ZIBRI_DI_TOKENS.MDX_EMAIL_COMPONENTS` names, and an `.mdx` file imports packages for the browser with `?client`. An alert as GitHub writes it, `> [!WARNING]`, is a blockquote whose component is handed the kind as `alert`, and the component of a code span or a code block is handed the code as written as `code`. The page's headings are its export `headings`, each an `MdxHeading` with its level, text and anchor, such as for a table of contents. The new package `zibri-mdx` builds these templates. Install it as a devDependency, which `zi add pages` does, so a deployment carries none of it. See [writing a page in markdown](https://service-soft.github.io/zibri/templates/templating/#writing-a-page-in-markdown).
- **Markdown at runtime.** `<Markdown source={...}/>` renders markdown the server gets while it runs, such as from a database, as a `.md` page renders it: through the components `ZIBRI_DI_TOKENS.MDX_COMPONENTS` names, with the same props, and its text escaped. It is never compiled, and html in it is a mistake only the render can see. An application switches it on with `renderAtRuntime` of `ZIBRI_DI_TOKENS.MARKDOWN_OPTIONS` and lists `zibri-mdx` in its dependencies, which it checks for while it starts. `MarkdownService`, replaceable through `ZIBRI_DI_TOKENS.MARKDOWN_SERVICE`, resolves the page. See [rendering markdown at runtime](https://service-soft.github.io/zibri/templates/templating/#rendering-markdown-at-runtime).
- **The rest of MJML's components.** `MjHero`, `MjTable`, `MjNavbar`, `MjSocial`, `MjCarousel` and `MjAccordion` with their parts, and in the head `MjBreakpoint`, `MjFont` and `MjHtmlAttributes`, which needs the package `cheerio`. Each nests where MJML lets it. See [rendering an email](https://service-soft.github.io/zibri/templates/templating/#rendering-an-email).
- **The nesting of an email follows your own components.** What a component renders is checked against the parent its use sits in, and what you pass it, its children or another prop, against where it places them. The build follows a component of another file to the file that declares it. Such a mistake is a `ZTSX004` warning, and fails the build from 4.0. See [nesting is checked at compile time](https://service-soft.github.io/zibri/templates/templating/#nesting-is-checked-at-compile-time).
- `renderPage` of `zibri-tsx` takes `contexts`, values of contexts for every component of the page.
- `TsxUtilities.renderPage` renders a page whose props are all optional without them.

### OpenAPI explorer
- **The explorer is a page of your application**, provided under `ZIBRI_DI_TOKENS.OPEN_API_EXPLORER_TEMPLATE`, in place of swagger-ui. It belongs to the `pages` feature and is styled with Tailwind like the other pages: `zi new` and `zi upgrade` write it into `src/templates/explorer/`, and delete the files of swagger-ui. A project that changed `custom.css`, `custom.js` or `swagger-ui-init.js` has a conflict to resolve. A project without `pages` serves the documents and no explorer, `/explorer` redirects to the OpenAPI document of the latest version, and `zi add pages` adds the explorer. A version of the application recorded under 3.0 lists the files of swagger-ui as routes, which a version bump does not count as removed. See [changing the explorer](https://service-soft.github.io/zibri/endpoints/open-api/#changing-the-explorer).
- **An AsyncAPI 3.0 document of the websocket events** of each version, at `/explorer/asyncapi/<version>`, which the explorer shows in a tab beside the OpenAPI document. `@Response` on a websocket route says what it answers with. `AsyncApiService` builds it, replaceable through `ZIBRI_DI_TOKENS.ASYNC_API_SERVICE`. See [the AsyncAPI document](https://service-soft.github.io/zibri/endpoints/async-api/).
- `WebsocketServiceInterface` has an optional `getPath`, the path the AsyncAPI document names. A websocket service of your own adds it to have the path in the document. It is required from 4.0.
- The explorer shows each version at `/explorer/<version>`, and a request sent from it names its version, so it reaches the routes of that version.
- An example of an XML body follows the `xml` of its schema: the names of its elements, its attributes, its namespaces and their prefixes. It is a document the route reads.
- A file sent as an attachment is offered to download, and a request may be sent to each server the document names with a full URL.
- **The OpenAPI document names a server**: the application, at `/`, with a description. `ZIBRI_DI_TOKENS.OPEN_API_SERVERS` names others in its place, and `ZIBRI_DI_TOKENS.ASYNC_API_SERVERS` does the same for the AsyncAPI document. The explorer starts each document with its servers and their descriptions. See [naming the servers](https://service-soft.github.io/zibri/endpoints/open-api/#naming-the-servers).
- `OpenApiExplorerUtilities` reads a document for the page, and resolves its references. A reference the document cannot resolve throws while the page renders, naming it.

### Endpoints
- **Filtering and ordering the list of a `CrudController`.** `findAll` takes an `order`, nested like the entity, `?order={"dueAt":"ASC","address":{"city":"DESC"}}`, by every string, number, boolean and date that is not excluded, encrypted, hashed or a password, in the entity and the objects inside it. An `OrderConfig` as `order` in the options names the properties, and reaches into a relation to one row. `order: false` takes none. A `FilterConfig` as `filter` in the options makes it take a `filter`, `?filter={"title":"invoice","project":{"name":"Website"}}`: it says for each property whether it matches by `'equals'`, `'iLike'`, `'fuzzy'`, `'oneOf'`, `'range'` or `'includes'`, and filters an object, the items of an array and a related row by the properties inside. Both are validated against the entity while the application starts, and each request against them. `FilterUtilities.resolveWhere` turns a filter into the where of a repository for a route of your own. See [filtering and ordering a list](https://service-soft.github.io/zibri/endpoints/creating-endpoints/#filtering-and-ordering-a-list).
- **An order reaches into an object property**, `order: { address: { city: 'ASC' } }`, on every data source, and sorts each value the way a property of its type on the entity sorts. See [filtering inside an object property](https://service-soft.github.io/zibri/data/data-source/#filtering-inside-an-object-property).
- **A `regex` needs no package of its own.** A declared `regex` runs in time linear to the value without `re2`, which a project can remove from its `dependencies` and its `allowScripts`. It matches what the same `RegExp` matches, where `re2` differed from it in places. With the `v` flag, a class matching strings of several characters, such as `[\q{abc}]`, is refused while the application starts. See [models](https://service-soft.github.io/zibri/data/models/).
- **The new package `zibri-contract`** holds the models a frontend shares with zibri, as they arrive as json, without the rest of the framework: the types of a filter and an order, `FilterConfig`, `FilterValue`, `OrderConfig` and `OrderValue`, which `zibri` exports as well, and `PaginationResult`, `ErrorResponseBody`, what the auth routes answer and take, logs and change sets. `LogLevel` and `ChangeSetType` of `zibri` are the enums of `zibri-contract`, and a check of the typecheck holds the models of `zibri` to the ones there.

### Application
- **A start waits for no index that only makes reads faster.** On Postgres, an index that is no unique, declared or kept for a relation or a search, is built once the application started, by one instance at a time under a lock of its own, and logged at `info` once built. On a large table a build takes minutes, which a start spent unable to answer, and an orchestrator restarting the instance as unresponsive cut short again and again. Uniques and checks are in place before the start is done, as before. A build the application is shut down during is built again by the next start. `PostgresDataSource.waitForIndexBuilds()` waits for them, which `startTestServer` of `zibri-testing` does after every start. See [keeping indexes and uniques](https://service-soft.github.io/zibri/data/data-source/#keeping-indexes-and-uniques).
- **A log names its application.** `Log` has an `application`, the `name` of the application options, so the logs of several applications in one table, like the ones a frontend sends to a route of yours, tell apart. A log written while no application runs has none. With `schemaManagement: 'migrations'`, the data source adds the column itself, see [upgrading from 3.0](#upgrading-from-30).
- **`stackTraceLimit`** says how many frames a stack trace keeps, in the process and in its thread jobs. It defaults to 50, which reaches your own code from inside a write to a data source, and a process started with another limit than node's 10, such as with `--stack-trace-limit`, keeps it. See [choosing how much of a stack trace to keep](https://service-soft.github.io/zibri/application/app-settings/#choosing-how-much-of-a-stack-trace-to-keep).
- A deployment carries none of what only building the application uses: `zibri` no longer names `typescript`, `ts-node`, `webpack`, `copy-webpack-plugin` and `mini-css-extract-plugin` as peers, and uses the application's own. A deployment pruned of its devDependencies had kept them, more than 40 MB. A deployment running TypeScript worker files with `enableTsWorkerFiles` lists `ts-node` and `typescript` in its `dependencies`. See [running TypeScript worker files](https://service-soft.github.io/zibri/background-work/multithreading/#running-typescript-worker-files).
- A loader the build of `zibri/webpack` uses, such as `ts-loader` or `css-loader`, that the application has not installed fails the build before it starts, naming the package to install.
- **An application without logins.** `authStrategies: []` registers no auth strategy, and no authenticator or two factor method unless the application names them, so an API open to everyone needs none of their configuration. A route that needs a login then stops the start, naming the route. An empty list was taken for a list left out, and given the default. `authenticators: []` and `twoFactorMethods: []` register none of theirs as well. See [registering strategies and authenticators](https://service-soft.github.io/zibri/auth/auth/#registering-strategies-and-authenticators).
- **`HttpClientBufferedBody`** sends bytes held as the chunks they were read in, such as one part of a large upload, with their `content-length` and without joining them into one buffer first. Every attempt and every redirect sends it whole again. See [setting the request body](https://service-soft.github.io/zibri/endpoints/http-client/#setting-request-body-query-and-header-params).
- **`validateRedirect`** of a request checks every redirect it follows, handed the URL it leads to, and fails the request when it throws, so that the address a redirect of a URL your users give you leads to is checked as the first one was. See [following redirects](https://service-soft.github.io/zibri/endpoints/http-client/#following-redirects).
- **Version 2 of backup transports.** `BackupTransportInterface` takes the versions a transport supports: `BackupTransportInterface<'v2'>` opens sessions that put, get, list and delete data under keys, knowing nothing of backups, and names `versions: ['v2']`. One session serves everything one resource of a backup or a restore does. `BackupTransportInterface` without a version is a transport of `v1`, as in 3.0, and one supporting both, `BackupTransportInterface<'v1' | 'v2'>`, is used as `v2`. The new `FsBackupTransport`, `S3BackupTransport` and `SftpBackupTransport` are built with a name and their options, and support both versions, as `BaseBackupTransport`, which they extend, does for any transport implementing `openSession`. Every backup keeps its keys, so what the transports stored before is found and restored where it is. A put is whole or nothing: the fs and SFTP transports write a resource into the folder `.partial` and rename it into place, as SFTP did the record alone, and the next backup deletes what an interrupted one left there after a day. A folder the application may not read, such as a disk's `lost+found`, is skipped with a warning when backups are synced, and `get` of a session fails with `BackupKeyAccessDeniedError` for it. The S3 transport deletes up to 1,000 objects in one request. The fs transport refuses a file larger than the size its backup recorded, as the others did. See [writing a transport of your own](https://service-soft.github.io/zibri/data/backup/#writing-a-transport-of-your-own).
- **Backups store unchanged data once.** A backup cuts each resource into chunks of about 1 MiB at boundaries its content decides, compresses each with zstd and, with `encrypt`, encrypts it under the repository key of the application, which each transport holds encrypted by the master key. A transport keeps each chunk once, so a backup stores the chunks no earlier backup stored: of a table only ever added to, what was added. 100 MB of rows took about 30 MiB per backup on a transport instead of 100 MB. Backups are written in format 2, under `.zibri-repository/` of each transport, and backups of format 1 are found and restored where they are. `BackupChunkEntity` records which chunks each transport holds: declare it beside `BackupEntity`, which with `schemaManagement: 'migrations'` takes a migration. Without it, each backup lists the chunks its transports hold first, and the application warns at boot. `ZIBRI_DI_TOKENS.BACKUP_CHUNKING_OPTIONS` sets the sizes of the chunks and the level. A blob store of your own implements `findNames` of a session as well, and no backup may be named `.zibri-repository`. `createBackupData` of a resource is handed `BackupDataOptions`, whose `chunked` says the backup cuts the data into chunks: a resource that compresses its data leaves that off then, since compressed data is not stored once. A Postgres data source dumps uncompressed then. Every file a backup or a restore stages in `BACKUP_TEMP_FOLDER` is compressed with zstd, and of a resource with `encrypt`, encrypted: what a backup stages and the snapshot of what the resource held under a key of their own, which the journal keeps encrypted by the master key for a snapshot, and the chunks a restore fetched as they were stored, under the repository key. A Valkey data source writes its keys in the order of their names, sorted in the `stagingFolder` of the options, encrypted, so that keys that did not change are stored once. See [storing unchanged data once](https://service-soft.github.io/zibri/data/backup/#storing-unchanged-data-once).
- **The space of deleted backups comes back.** `BackupGarbageCollectionCronJob`, registered for you, deletes once a day what the backup transports hold that no backup needs: the chunks only deleted backups named, and what backups that never finished stored. While it deletes, a resource waits a few seconds at a time to be stored, and a restore goes on. It forgets a chunk recorded as stored that a transport does not hold, so the next backup stores it again, and logs every backup naming one as an error. `collectGarbage` of `BackupServiceInterface` runs it at once, which is optional until 4.0 for a backup service of your own. With `ZIBRI_DI_TOKENS.BACKUP_SCRUB_OPTIONS`, it also reads the stored chunks back over `cycleInDays` and checks each, deleting one that changed. See [freeing the space of deleted backups](https://service-soft.github.io/zibri/data/backup/#freeing-the-space-of-deleted-backups).
- **Backups read only what changed.** A Postgres data source with `incrementalRead: true` reads only the rows that changed since the backup before, through logical decoding, written through a repository or not, rather than dumping everything each time. A restore applies the backup in full it builds on and every backup after it, in one transaction. The first backup of each week reads in full, or of each period `fullRead` of `BackupRetention` names, as does the next one after a restore or a change of the schema. A backup starts once the transactions writing when it began have ended, and warns every 10 seconds while one is open, naming it. The retention keeps every backup a kept one builds on, and `delete` refuses a backup another one builds on with a `409`. The data source checks at boot what the server and the role backups run as need: `wal_level` `logical`, `max_slot_wal_keep_size` set, two free replication slots, a database encoded in `UTF8`, and a role allowed to replicate and to set `session_replication_role`, with `CREATE` on the database and owning the tables read through the changes. `BackupResourceEntity` records the backup it builds on and where the next one reads on from. A resource of your own reads only what changed by implementing `IncrementalBackupResourceInterface`. The Postgres container of `zibri-testing` runs with `wal_level` `logical`, and grants the role what `incrementalRead` needs when the data source sets it. See [reading only what changed](https://service-soft.github.io/zibri/data/backup/#reading-only-what-changed).
- **Backups of a tenant.** `queueBackup({ tenantId })` backs up the rows of one tenant, as they are stored and as of one moment, in every data source marked with `@Backup` that holds rows of tenants, to the tenant's own transports, and `restore` of it replaces exactly the tenant's rows in each data source in one transaction while every other tenant goes on working. Shared rows are never touched, and the rows of append-only and chained entities stay as they are. A row such a row points at is written over in place, and kept when it was created since, soft deleted where its entity soft deletes; a value of a unique it holds that the backup gives to another row gives way to a stand-in, such as `<value>_<moment of the restore>` for a text, and a warning names the kept rows. `restoreBackup` of `BackupResourceInterface` gets a function reading the data again. The restore is recorded in the tenant's audit trail as `backup.tenant.restored`, and the retention counts each tenant's backups apart from the application's. `BackupEntity` records the tenant. See [backing up a tenant](https://service-soft.github.io/zibri/data/backup/#backing-up-a-tenant).
- **Exporting a tenant.** `exportTenant` of `BackupServiceInterface` writes the rows of a tenant as the application answers them, readable without it: a tar archive of a manifest and a folder per data source holding a file per entity, in JSON lines or CSV. In CSV, text a spreadsheet would run as a formula starts with a `'`. Encrypted values are decrypted, hashed and excluded properties left out. It is optional until 4.0 for a backup service of your own. See [exporting a tenant](https://service-soft.github.io/zibri/data/backup/#exporting-a-tenant).
- **A tenant's own storage for its backups.** With `TenantBackupTransport` declared, `createTenantBackupTransport` adds storage a tenant keeps its backups on, of a kind the application lists: a bucket over https, `S3TenantBackupTransportKind`, an SFTP server, `SftpTenantBackupTransportKind`, or a kind of your own implementing `TenantBackupTransportKindInterface`, whose settings and secret are checked against the models it names and whose every host is checked through the `TenantTransportNetwork` it is handed. Its secret is encrypted and bound to the row, written to and deleted from once so that a wrong one is refused at once. A tenant's backups go there alone, encrypted with a repository key of the tenant's own, and a backup of a tenant without one is refused; the garbage collection goes through them too, and records the backups they hold that the database does not, such as after it was restored, as does one instance as the application starts for the transports no recorded backup names. `syncTenantBackupEntities` records those of one tenant at once. A host leading to this machine or a private network is refused when it is added and before every session, and so is a redirect a bucket answers with and a bucket name that is no name of a bucket; `ZIBRI_DI_TOKENS.BACKUP_TENANT_TRANSPORT_OPTIONS` narrows the kinds and hosts, or with `allowPrivateNetworks` lets tenants reach inside. With `TenantBackupSettings` declared, `setTenantBackupRetention` keeps a tenant's backups by a retention of its own. The methods are optional until 4.0 for a backup service of your own. See [letting a tenant back up to its own storage](https://service-soft.github.io/zibri/data/backup/#letting-a-tenant-back-up-to-its-own-storage).
- **`REPEATABLE READ` on Valkey.** A transaction of a `ValKeyDataSource` started with `REPEATABLE READ` reads every row as it was at its first read: each write through the data source meanwhile copies the row it writes first, which the transaction reads, and the server holds those copies until it ends. Its commit fails with a `TransactionSerializationError` when another transaction wrote a row it writes since. `SERIALIZABLE` runs as `REPEATABLE READ` with a warning, and `READ COMMITTED` no longer warns. Both levels were ignored with a warning. See [differences to a SQL data source](https://service-soft.github.io/zibri/data/data-source/#differences-to-a-sql-data-source).
- **A Valkey restore in place.** A `ValKeyDataSource` marked with `@Backup` sets `restoreMode`. `'staged'` writes the backup beside what is stored and swaps it in at one moment, as every restore did: the server holds both until then, and answers nothing else while it swaps. `'direct'` deletes what is stored and writes the backup in its place a batch at a time, while the server goes on answering: it needs no memory beyond what the backup holds, a reader meanwhile sees part of the backup, and a restore that fails part way is put back from its snapshot. A restore of a tenant follows it: `'direct'` replaces the tenant's rows a batch at a time rather than in one transaction, which holds every row in the application until it commits. Without `restoreMode`, the application warns at boot and restores `'staged'`. See [backing up a data source](https://service-soft.github.io/zibri/data/backup/#backing-up-a-data-source).
- **A restore is told whether there is room for it before it starts.** Each backup records of each resource what it took as staged, `stagedSize` of `BackupResourceEntity`. Once a backup is completed, the instance that completed it logs a critical error when its disk could not restore it. A restore checks the disk of `BACKUP_TEMP_FOLDER` before it fetches anything, and again before it takes the copies it puts back from, and is refused with a `NotEnoughRestoreSpaceError` that names what each resource takes, what is free, and every way to go on with what each gives up. A disk that runs out while a restore fetches or copies ends it with the same error before anything changed, and is no longer tried on the next transport. A Postgres server that runs out of disk replacing the tables, and a Valkey server that runs out of memory staging a backup, fail the restore saying what they hold, what replacing it takes and what to do. `restore` takes `RestoreOptions`: `resources` restores the named resources alone, `putBack: false` keeps no copies, `deleteFirst` deletes what each data source holds before the backup is applied, which a resource of your own implements with `deleteBackedUpData` of `BackupResourceInterface`, and `skipSpaceCheck` goes on regardless. See [sizing the server for backups and restores](https://service-soft.github.io/zibri/data/backup/#sizing-the-server-for-backups-and-restores) and [restoring with less room](https://service-soft.github.io/zibri/data/backup/#restoring-with-less-room).
- **A restore of one data source needs half the disk.** A restore of a single resource whose restore changes everything or nothing by itself keeps no copy of the current data to put back. A Postgres data source restores so when the backup records exactly the migrations of the build, read from the dump before anything is applied, and no backup after the one in full it builds on records a migration, a Valkey data source with `restoreMode: 'staged'` when its backup does, and a backup of a tenant does, except on a Valkey data source with `restoreMode: 'direct'`. A resource of your own says so with `resolveRestoresWhole` of `BackupResourceInterface`. See [a restore of several resources](https://service-soft.github.io/zibri/data/backup/#a-restore-of-several-resources).
- `resolveApplicationPackage` loads a package a plugin leaves to the application, failing with the feature it was needed for and the command that installs it.
- **Commands of your own.** `commands` of the application options lists `AppCommand`s, which `runCommand` runs in place of starting, named by the first argument, such as `node dist/bundle.js deactivate-user ada@example.com`. An application with commands warns about a first argument that names none of them, listing them, and starts. From 4.0 it refuses one. See [commands](https://service-soft.github.io/zibri/application/commands/).
- **Logging everybody out.** `endEveryLogin` of `AuthServiceInterface` ends every login of every user, in every strategy, recorded as `auth.every-login.ended`. A login strategy of your own implements `endEveryLogin` of `LoginAuthStrategyInterface`, which is optional until 4.0. So are `endEveryLogin` and `setPassword` on `AuthServiceInterface`, for an auth service of your own. See [logging everybody out](https://service-soft.github.io/zibri/auth/auth/#logging-everybody-out).
- **The code that enrolls a one time password finishes the login too.** A user enrolling their first second factor at login presents the same code at `POST /login/2fa/confirm`, rather than waiting for the authenticator to show the next one. See [asking for a second factor at login](https://service-soft.github.io/zibri/auth/two-factor/#asking-for-a-second-factor-at-login).
- **One route for every email link.** `POST /confirm-email` of the `AuthController`, there with `confirmEmailRoute: true` beside `emailVerification` in its options, confirms a link of either purpose, as `confirm-email-verification` and `confirm-email-change` do, and answers an `EmailConfirmation`: what the link was for and whether that is done. The links look alike, so the page they open couldn't tell which route to call. `confirmEmail` of `EmailVerificationServiceInterface` does it, which is optional until 4.0 for a service of your own, and an application asking for the route with a service without it refuses to start. See [verifying email addresses](https://service-soft.github.io/zibri/auth/email-verification/#setting-it-up).
- **The previous address approves a change.** With `previousAddressConfirms` of `EMAIL_VERIFICATION_OPTIONS`, a change of an address mails a link to the previous address as well, and takes effect once both links were followed, in either order. Off by default. The template of `verificationEmail` is given the `purpose` `change-approval` for it, and `EmailVerificationToken` stores the links of a change that were followed. `EmailVerificationPurpose` gains `'change-approval'` for it: a template that switches over every `purpose` needs a case for it to compile, which it is only ever given with `previousAddressConfirms`. See [changing an address](https://service-soft.github.io/zibri/auth/email-verification/#changing-an-address).
- **Setting a password for a user.** `setPassword` of `AuthServiceInterface` sets a password without the one the user has, lifts a lock of wrong passwords, ends their logins and is recorded as `auth.password.set`. With `requireChange` the user chooses their own at their next login. See [setting a password for a user](https://service-soft.github.io/zibri/auth/auth/#setting-a-password-for-a-user).
- **`GET /me`** of the `AuthController`, there with `currentUserRoute: true` in its options, answers the logged in user as a `CurrentUserProfile`: their id and email, when they verified it, their `platformPermissions`, and their active `memberships`, each a `CurrentUserMembership` with the `permissions` of its tenant, so a frontend shows only what the user may do and switches tenants without asking again. `resolveCurrentMemberships` of `AuthServiceInterface` resolves them, which is optional until 4.0 for an auth service of your own. See [checking permissions in a frontend](https://service-soft.github.io/zibri/auth/roles-and-permissions/#checking-permissions-in-a-frontend).
- **`GET /2fa/registrations`** of the `AuthController`, there with `twoFactorRegistrationsRoute: true` in its options, answers the two factor methods the logged in user has enrolled, as `TwoFactorRegistrations`. See [enrolling a user](https://service-soft.github.io/zibri/auth/two-factor/#enrolling-a-user).
- A route guarded by `@Auth.require2fa` called without a second factor answers `401` with the name `SecondFactorMissingError`, so a frontend asks its user for a code instead of refreshing the login. A two factor method of your own throws it when its header is missing. See [what a second factor is for](https://service-soft.github.io/zibri/auth/two-factor/#what-a-second-factor-is-for).
- `ErrorResponseBody`, the JSON body an error is answered with, is exported.
- **A wait that goes on says what it waits for.** A lease taken with `mode: 'wait'` warns every 30 seconds while somebody else holds it, naming the key, the instance holding it and until when, and `waitForBackup` warns where the backup stands: each resource stored or not, its failed attempts, when the next is due and what the last failed with. A `PostgresDataSource` reading its data for a backup or for the copy a restore keeps warns where the read stands: the step it is at, whether it waits for the backup to read on, and what each busy connection to the database waits for, naming the connections holding a lock one waits for. A query it names is logged with each string in it as `'*****'`. `ZIBRI_DI_TOKENS.WAIT_REPORT_INTERVAL_IN_MS` sets how often. See [choosing how a lease is acquired](https://service-soft.github.io/zibri/data/leases/#choosing-how-it-is-acquired-and-released).

### Fixed
- **The stack trace of a logged error is only in its `stackTrace`.** `errorToLoggedError` put it into the `paragraphs` as well, so an email of a log, or a log history that shows both, showed it twice. `stackTrace` now holds the stacks of the causes too, after the one of the error, and the console prints it after the paragraphs as before.
- **A stream of more than 500 rows in a Postgres transaction waited forever.** It reads the rows back a batch at a time, and in a transaction the read of a batch queued behind the stream on the transaction's one connection. It reads through a cursor declared in the transaction now, which leaves the connection free between batches, so whatever the reader runs in the transaction goes on as well.
- **Deleting rows that other rows point at read the pointing table once for every row deleted, on Postgres.** Postgres indexes the key a foreign key refers to and not the column holding it, so deleting many rows pointed at from a large table ran into the statement timeout, as a restore of a tenant deleting its change sets did. The column of every `manyToOne` and `belongsToOne` is indexed now, unless an index or unique the entity declares starts with it, and `ChangeSet` is indexed by the row it describes. The indexes are built once the first instance of 3.1 started, which waits for none of them. An instance of 3.0 started beside it leaves them alone.
- **A Postgres connection ended by the server while it was in use ended the process.** A connection taken out of the pool had no listener for its failure, so a restart of the database, or a connection terminated by an administrator, between two statements of whoever held it, crashed the application. It is logged now, and whoever holds the connection learns from its next statement failing.
- **What was encrypted after a restore of the application could be unreadable after the next start.** The restore brought back the data keys as the backup held them, while every instance running went on encrypting with the key it had read before, which the backup lacked after restoring onto a fresh database or after a key rotation since the backup. A restore keeps the data keys and signing keys stored when it began beside those of the backup, the default ones staying the default, and the next start writes them back when the restore was killed before it did. An encryption service of your own implements `resolveKeptKeys` and `putBackKeptKeys`, optional until 4.0. See [encrypting backups](https://service-soft.github.io/zibri/data/backup/#encrypting-backups).
- The first requests after a restart of a Postgres server could answer `500`: a connection the server ended tells its client a moment later, and a statement taking it before then failed, and gave the connection back to the pool. A statement outside a transaction whose connection the server ended before it committed, `57P01`, `57P02` or `57P03`, or that failed before it was sent, runs again on the next connection, and the ended one is closed. One that may have committed, on a connection that ended without saying why, fails as it did. See [when the database cannot be reached](https://service-soft.github.io/zibri/operations/incidents/#when-the-database-cannot-be-reached).
- An instance applied a cache invalidation it published itself a second time at its next poll, emptying what was cached since a couple of seconds after the first time. It applies its own once, as it publishes it.
- **After a restore, every instance went on answering from what it held in memory before.** A restore replaced the rows without invalidating any tag, so the caches answered with what the restore had replaced until their entries expired, and a restore of the application left the roles as they were, so a permission taken from a role since the backup was still granted until the next start. Once a restore is done or put back, every cache is emptied after one of the application, and after one of a tenant, what was cached for the tenant and outside every tenant, on every instance. Every entry carries the tag of the tenant it was written for, and `CacheRestoreTagUtilities` names the tags, which a listener of `registerInvalidationListener` keeping rows in memory listens for. A cache store of your own keying by `cacheKeyOf(key, false)` sets `perTenant: false` in its `config`. See [restoring a backup](https://service-soft.github.io/zibri/data/caching/#restoring-a-backup).
- **For up to 20 seconds after a restore of the application, an event did not reach the subscribers of other instances.** The restore brought back the registrations of the subscribers as the backup held them, lapsed or missing those added since, so an event emitted before each instance renewed its own owed them no run, and one the backup held unfinished was settled without them. `EventSubscriberRegistration` is declared `backedUp: false`, and a restore keeps the registrations of the instances running. Other instances keep running while a restore runs, see [restoring while other instances run](https://service-soft.github.io/zibri/data/backup/#restoring-while-other-instances-run).
- **A restore of the application brought back the logins and credentials of the backup's moment.** A login ended since the backup worked again, and one started since was gone; a password changed since stopped working while the one before worked again, and an api key, passkey or second factor revoked since was back while one created since was gone. The logins, what a login under way holds and the counts of failed attempts and rate limits are declared `backedUp: false`, and a restore keeps them as they are. The credentials are declared `backedUp: 'keptForCurrentUsers'`, a new value of `backedUp`: a restore keeps those of every user that exists when it begins, and those of the backup come back for the users that did not exist then, such as on a fresh database. `OAuthProviderTokens` is declared `backedUp: { keptWith: () => FederatedIdentity, by: 'identityId' }`, another new value: a restore keeps a row exactly when it keeps the row it names. The next start writes them back when the restore was killed before it did. A user service of your own implements `streamUserIds` and `findStoredUserIds` of `UserServiceInterface`, optional until 4.0. See [keeping rows across a restore](https://service-soft.github.io/zibri/data/backup/#keeping-rows-across-a-restore).
- **After a restore of the application, a reconnecting websocket client missed the messages sent since.** The restore set the seq of the messages back, so the next messages were given seqs the client already had, and a replay after its `offset` left them out until the seqs passed it. A client whose `offset` is past the newest message is sent `ws:replay-incomplete`, and reloads. See [reconnecting](https://service-soft.github.io/zibri/endpoints/websocket/#reconnecting).
- **A restore held the data of an encrypted resource unencrypted on the instance's disk.** What it fetched, and the snapshot of what each resource held, were written as they were, while the documentation said the disk never holds that data unencrypted. Both are encrypted now, as the staged copy of a backup is. See [a restore of several resources](https://service-soft.github.io/zibri/data/backup/#a-restore-of-several-resources).
- **A resource a failed restore could not put back was left to be put back by hand.** Its snapshot was removed 12 hours later, and a restore before that could write over it. The next start puts it back, the way it puts back a killed restore, and every restore on the instance is refused with a `409` until then. See [a restore of several resources](https://service-soft.github.io/zibri/data/backup/#a-restore-of-several-resources).
- **Sorting the names of the keys of a large Valkey data source held a file open for every 4 MiB of names.** A backup of 100 million keys merged about 3 000 files at once, each with a buffer, which could run into the limit of open files. It merges at most 64 at once, in several passes when there are more.
- A `RedirectResponse` of a route registered with `registerRoute` and `useInOpenApi: false` was answered with `200`, which no browser follows. It is answered with `303 See Other`, as `@Response.redirect` defaults to.
- A request refused for a missing CSRF token answered with the name `ForbiddenError`. It answers `CsrfTokenRefusedError`, as the documentation said, so a frontend fetches the token and retries instead of giving up.
- The documentation named `DELETE /auth/2fa/{method}` for removing a second factor, which is `DELETE /auth/2fa/registration/{method}`, and listed only login and the password reset as rate limited.
- The comment of `rollbackToChangeSet` said the given change set is deleted. It is kept, and only the change sets after it are deleted.
- A response the http client streamed, such as a backup restored through the S3 transport, ended the process when the server closed the connection while the body was read slower than it arrived: Node's bundled `fetch` threw an assertion nothing could catch. The client sends with `undici` 8, which zibri now depends on. A `dispatcher` an application hands it is built from `undici`, see [egress](https://service-soft.github.io/zibri/endpoints/http-client/#egress-proxies-ca-bundles-and-mutual-tls).
- The SFTP backup transport stored a backup at about a tenth of the speed it read one back, sending one write at a time and waiting for each. It keeps up to 2 MiB of writes in flight.
- A backup or restore over SFTP waited forever for a server that kept the connection up and answered no request, that logged it in and never opened the SFTP session, or that closed the connection while it logged in, as a server refusing the address it comes from can. A connection closed before the login completed fails at once, naming the server. The transport ends the connection once the server answered nothing for 60 seconds, `requestTimeoutInMs` of its options, and the backup fails with an error naming what it waited for. Opening the SFTP session fails after `connectTimeoutInMs`, 20 seconds, as connecting and logging in do. See [storing backups on an SFTP server](https://service-soft.github.io/zibri/data/backup/#storing-backups-on-an-sftp-server).
- The S3 backup transport held each part of an upload four times over while it was sent, and kept the part it had sent while it gathered the next. It holds the one part it gathers or sends, and sends it from the chunks it was read in: a backup of 100 MB peaks at about 95 MiB rather than 200, and one of 10 MB at about 33 MiB rather than 65.
- A thread job queued while a worker was ending, such as right after a job threw where nothing could catch it, waited beside the worker started in its place until the next poll. It starts on that worker.
- **A valkey transaction whose commit took longer to send than its locks live failed with `TransactionLocksLostError`**, as one of 140,000 rows did: the renewals sent meanwhile waited behind the commit. They are sent over a connection of their own, so the locks stay alive however long the commit takes to send.
- A thread job whose worker ended between being taken for the job and getting it, as one killed for its memory or by a native crash can, was sent to the dead worker and waited for its timeout, an hour by default. The claim is handed back, and the job starts on the worker started in its place.
- A backup whose resources finished storing together was completed once per resource: its record was stored as many times, and the retention applied as often.
- A restore of a backup right after `waitForBackup` handed it back could be refused with a `409`, naming a resource as being backed up: the backup completed while that resource still let go of what it held while it was stored.
- An instance stored every resource of the backups that were due at once, each with a staging file as large as the resource and, for a database, a dump running. It stores `ZIBRI_DI_TOKENS.BACKUP_MAX_CONCURRENT_RESOURCES` at once, 1 by default, and the others one after another or on instances that have room. See [creating and restoring backups](https://service-soft.github.io/zibri/data/backup/#creating-and-restoring-backups).
- A Valkey backup with `backupMode: 'walk'` read each key as it was when it got to it, so a transaction committed meanwhile could be in it with some of its rows and without others, and a unique value moved from one row to another could be in it twice, which its restore refused, as did a start of the application over what it restored. It reads every key as it was when it began: a write through the data source copies the key it writes first, once, which the server holds until the backup ends. A write past the data source, through `connection`, copies nothing, and a backup that read two rows holding the same unique value that way fails rather than being stored. See [backing up a data source](https://service-soft.github.io/zibri/data/backup/#backing-up-a-data-source).
- A Valkey transaction whose hold on the rows it wrote lapsed, such as in a pause of its process longer than the hold, warned and committed all the same, over what another transaction had written to those rows meanwhile. Its commit fails with a `TransactionLocksLostError`, a `TransactionConflictError`, and applies nothing, so `runInTransaction` runs the work again. See [differences to a SQL data source](https://service-soft.github.io/zibri/data/data-source/#differences-to-a-sql-data-source).
- A restore of a Valkey data source sent a request per key and waited for each, and built a transaction of every key to swap them in. It restores 250 keys a request, and the server swaps them in on its own.
- A backup of a Valkey data source with `backupMode: 'snapshot'` arrived as one reply, which the application held whole while it stored it: 100 MB peaked at about 250 MiB more. The server copies the keys at one moment, and the copies are read a batch at a time. The server needs the memory for that copy while the backup is taken, and a backup is refused when it has less free than that, rather than having the server evict your keys for the copies. See [backing up a data source](https://service-soft.github.io/zibri/data/backup/#backing-up-a-data-source).
- A backup of a Valkey data source took the keys a restore stopped part way had left staged, and a restore of it staged them again.
- A backup and a restore of a Valkey data source held every set whole three times over, such as the ids of a table: about 12 MiB at 100 000 rows. A set of more than 1 000 members is read and restored 250 members at a time. A walk reads it from a copy of it alone, made at one moment, and fails when the server has no room for that copy. Backups taken before are restored as they are. See [backing up a data source](https://service-soft.github.io/zibri/data/backup/#backing-up-a-data-source).
- The copies of a Valkey snapshot, and the keys a Valkey restore staged, stayed on the server for good when the process taking them died part way. The next snapshot or restore of the data source deletes them, once the one that held them has not been heard from for 15 minutes. A restore that went unheard for that long itself fails rather than swapping in what may be left of its keys, and so does a snapshot rather than storing a backup lacking some.
- A Valkey backup with `backupMode: 'walk'`, and a restore while it rebuilds the ids, indexes and uniques, held the name of every key at once. They read the keys a page at a time.
- `deleteKey` and `deleteAllKeys` of the encryption service refuse a data key that stored values or recorded backups still need, with an `EncryptionKeyInUseError`. They deleted it, and what it encrypted could not be read again. `allowInUse: true` deletes it regardless. See [rotating a key](https://service-soft.github.io/zibri/data/encryption-and-hashing/#rotating-a-key).
- A build started outside the project, such as `webpack -c api/webpack.config.js` in the root of a monorepo, wrote the types of the handlebars templates and the generated entities of the folder it was started in. It writes those of the project its `webpack.config.js` names, as it did the translation source.
- In an application, the types of zibri built on express, such as `HttpRequest`, on the OpenAPI document, such as `OpenApiSchemaObject`, on pdfmake, such as the document definitions of `PdfUtilities`, and on ws were `any`, as the packages declaring them were not installed with zibri. They are typed, so code that passed something else there is now a type error. The OpenAPI types are zibri's own: an extension, a field starting with `x-`, is `unknown`, and the scopes of an OAuth2 flow are descriptions, strings.
- An element whose tag a variable holds, such as `const Tag = 'img'; <Tag src={src}/>`, was written without the closing slash the same element written by its name has. It is written the same now.
- The jest transform `zibri-tsx-compiler/jest` cached a page written in markdown under the same key after `zibri-mdx` was updated, so a test rendered what the `zibri-mdx` before printed. It compiles the page again.

- A handler a nested component wraps, such as `onClick={() => onClick?.(value)}`, never ran under the Content Security Policy zibri sends. It runs.
- `MjRaw` was refused directly in `Mjml`, `MjHead`, `MjBody`, `MjWrapper`, `MjSection` and `MjGroup`, where MJML allows it. It is accepted there: in `MjHead` it adds its html to the head, and directly in `Mjml` with `position="file-start"` it writes it before the doctype.
- The `cssClass` of `MjText` was set on the `div` of its text, where MJML sets it on the cell around it. It is set on the cell, so a style or an `MjSelector` matches what it matches in MJML.
- An email imported the font Ubuntu whichever fonts it used. It imports a font MJML knows, such as Ubuntu or Roboto, when its body uses it, as MJML does.

The callbacks run once every component is set up, each on its own. Code reading a variable right after the `onClient` assigning it reads it in the callback instead.

## 3.0.0

A major release. An application on 2.x needs changes before it starts on 3.0.0, and its database needs a migration. [Upgrading to 3](https://service-soft.github.io/zibri/releases/upgrading-to-3/) lists both: what the compiler does not tell you about, and the migration for the tables Zibri ships. Back up your database first.

Zibri 3 needs node 24 or newer.

### New packages
- **`zibri-tsx`** compiles the `.tsx` templates of pages and emails at build time, in place of preact. A component can carry code that runs in the browser. See [templating](https://service-soft.github.io/zibri/templates/templating/).
- **`zibri-testing`** starts your application in a test with the router, auth, lifecycle and error handling production has. Its in-memory data source needs no database, and it starts Postgres and Valkey containers or a cluster of instances when a test asks for them. See [testing](https://service-soft.github.io/zibri/testing/).
- **`zibri/internal`** is a second entry point of `zibri`, for what only a data source, driver, parser or router of your own needs. See [releases](https://service-soft.github.io/zibri/releases/releases/#what-is-public).

### Generating and upgrading a project
- `zi new` writes a project that builds, tests and runs as it stands, with a Dockerfile, a CI workflow and its configuration read from the environment. Pages, mailing lists, a metrics dashboard and a log email are features you choose.
- `zi add` and `zi remove` add or remove a feature later.
- `zi upgrade` merges what a new release generates into your project, the way git merges a branch.
- `zi migrate` creates a migration from what your entities changed, and records a baseline.
- The build, the jest configuration and the compiler options come from the packages: `zibri/webpack`, the `zibri-testing` preset and `zibri/tsconfig.application.json`. Updating the packages updates them.
- A deployed image names the source file and line in every stack trace.

See [getting started](https://service-soft.github.io/zibri/getting-started/) and [the generated project](https://service-soft.github.io/zibri/application/project-layout/).

### Data
- **Postgres without TypeORM.** The Postgres data source talks to `pg` itself and builds its queries itself. How the schema is managed, TLS and the pooler in front of the database are options you set. See [data sources](https://service-soft.github.io/zibri/data/data-source/).
- **Valkey data source**, with the same repositories as Postgres.
- **Tenants.** Every row belongs to a tenant or is shared, and every read and write stays inside the tenant of the request. See [tenants](https://service-soft.github.io/zibri/data/tenancy/).
- **Transactions across data sources**, and a `TransactionConflictError` for a deadlock or a serialization failure.
- **Tamper-evident tables.** Append-only entities, and chained entities whose rows form a hash chain. See [tamper-evident tables](https://service-soft.github.io/zibri/data/tamper-evident-tables/).
- **What a call costs.** Every repository call has a documented number of round trips. See [costs](https://service-soft.github.io/zibri/data/costs/).

### Logging in
- **Single sign-on** through OpenID Connect (Google, Apple, Microsoft Entra ID, Keycloak), plain OAuth2 (GitHub) and SAML 2.0. See [login through a provider](https://service-soft.github.io/zibri/auth/login-through-a-provider/).
- **Directory login** against LDAP, such as Active Directory. See [login through a directory](https://service-soft.github.io/zibri/auth/login-through-a-directory/).
- **Passkeys**, to log in and as a second factor, and recovery codes beside TOTP. See [passkeys](https://service-soft.github.io/zibri/auth/passkeys/) and [two factor](https://service-soft.github.io/zibri/auth/two-factor/).
- **Services calling your API** with [API keys](https://service-soft.github.io/zibri/auth/api-keys/), [client certificates](https://service-soft.github.io/zibri/auth/client-certificates/), [tokens your application issues](https://service-soft.github.io/zibri/auth/authorization-server/) or [tokens of your identity provider](https://service-soft.github.io/zibri/auth/provider-tokens/). Tokens can be bound to a key with [DPoP](https://service-soft.github.io/zibri/auth/dpop/).
- **Roles and permissions.** Roles are rows, permissions are declared in code, at the tenant or the platform level, with wildcards. See [roles and permissions](https://service-soft.github.io/zibri/auth/roles-and-permissions/).
- **SCIM provisioning** from a tenant's identity provider. See [SCIM](https://service-soft.github.io/zibri/auth/scim/).
- **Email verification**, a required password policy, scrypt as the default hash, and an optional lock after too many wrong passwords. See [verifying email addresses](https://service-soft.github.io/zibri/auth/email-verification/) and [auth](https://service-soft.github.io/zibri/auth/auth/).
- **`AuthController`** defines the auth routes. See [the auth routes](https://service-soft.github.io/zibri/auth/auth-routes/).
- **Audit trail.** Logins, refused routes, password resets and role changes are recorded in a tamper-evident trail. See [audit trail](https://service-soft.github.io/zibri/data/audit/).

### Running in production
- **Several instances.** Cron jobs, events, mails and named locks are claimed through [leases](https://service-soft.github.io/zibri/data/leases/), so every instance is equal. See [replication](https://service-soft.github.io/zibri/data/replication/).
- **Tracing** through OpenTelemetry, and metrics labeled by route. See [tracing](https://service-soft.github.io/zibri/operations/tracing/) and [metrics](https://service-soft.github.io/zibri/operations/metrics/).
- **Backups** to S3 and SFTP beside a folder, encrypted, and key rotation for encrypted properties. See [backup](https://service-soft.github.io/zibri/data/backup/) and [encryption and hashing](https://service-soft.github.io/zibri/data/encryption-and-hashing/#rotating-a-key).
- **Limits on requests and statements**, and an HTTP client that stops calling an upstream that keeps failing.
- **XML** request and response bodies, validated against a model like JSON. See [XML](https://service-soft.github.io/zibri/endpoints/xml/).
- **Recovering failed work.** A failed cron job, event, thread job, mail or backup keeps what it failed with, and can be started again. See [recovering work that stopped](https://service-soft.github.io/zibri/background-work/troubleshooting/).

### Packages you install
Zibri installs only what every application needs. The package of each feature, such as `pg`, `nodemailer` or `socket.io`, is installed by the application that uses it, and the application names a missing one while it starts. See the respective Requirements section of each feature.
