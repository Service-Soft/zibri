# Changelog

What changed in each release of `zibri`, `zibri-contract`, `zibri-tsx`, `zibri-tsx-compiler`, `zibri-mdx`, `zibri-testing` and `zibri-cli`. They are released together, at one version.

## 3.3.0

### Upgrading from 3.2
- **Run `zi upgrade` to read the variables of your project through `env`.** It writes `env` into `src/env.ts`, and the reads into each file `zi new` wrote, merged like every other change: a file you never changed is replaced, a reader you added at the end of `src/env.ts` stays, and a line you changed where the release changed it too gets conflict markers to resolve. A file that keeps reading its variables by name works as before, as `requireEnv` and the other readers by name stay exported. Move a read of your own by hand: add the variable to `Env` and a getter to `env` in `src/env.ts`, and replace `requireEnv('COLLECTOR_URL')` with `env.collectorUrl`. A lint configuration with `@typescript-eslint/no-deprecated` names every read by name that is left.
- **A final number issues an invoice, and the invoices issued before get their `issuedAt` on the first start.** A write of a repository leaving an invoice or credit note with a final number, one not starting with `TEMP` and the `separator`, and no `issuedAt` gives it its `date` as its `issuedAt`, and issues it in its transaction: posted with the bookkeeping plugin, archived with `archive`, and read only with `issuedInvoicesReadOnly`. A write that cannot give such an invoice its own `date` is refused with a `409`: one to every invoice a filter matches, when it matches more than one, an `updateEach` of several invoices that names them by no `id`, and an `upsert` that updates a stored invoice. Name the `issuedAt` in such a write, or write the invoice by its id. On every start, each invoice of every tenant with a final number and no `issuedAt` is given its `date` as its `issuedAt`: the invoices stored before, and those an instance of 3.2 stores during a rolling deploy. They are not posted into the books, their documents are not archived, and `issuedInvoicesReadOnly` does not refuse the write: they were issued already. A start finding none changes nothing. From then on they are credited, matched with the bank plugin and listed as issued like the invoices issued since. With `schemaManagement: 'external'` and a table of `Invoice` without `issuedAt`, no invoice is issued until the column is added, see [data](#data).
- **The mails of the framework are in the locale of their recipient.** A user without a `locale`, such as one created before the upgrade, gets them in the `defaultLocale`, where a password reset, a link verifying an address and a second factor code were in the locale of the request sending them. Set their `locale` with `updateLocale` of the user service. A password reset template, an invitation template or a `deliver` of a code method of your own renders in that locale too. With a `LocalizeServiceInterface` of your own that has no `runInLocale`, they stay in the locale of the request sending them.
- **Keep the `seq` of a websocket message only when it has one.** A message sent with `persist: false`, such as the answer to a message of the client, carries no `seq`, see [fixed](#fixed). A client of your own that keeps the `seq` of the last message it received as its `offset` keeps it from the stored ones: `lastSeq = message.seq ?? lastSeq`. A `WebsocketResponseHandler` of your own is handed such a message too, a `SentWebsocketMessage`, whose `seq` is undefined whatever type its parameter names.
- **Rename a property of your own entities that the framework declares.** `BaseUserEntity()` declares `kind`, whether a user is a person or a service account, see [auth](#auth), and `locale`, see [localization](#localization), `BaseInvitationEntity()` declares `locale`, `withoutPassword` and `rowShares`, and `Invoice` declares `type`, `precedingInvoices` and `issuedAt`, see [invoicing plugin](#invoicing-plugin). A property of the same name in a class of yours extending one of them clashes with it.
- **Handle the new members of `AuditAction` and `AuditReason` in a switch of your own that names every member.** `AuditAction` has `auth.login-link.requested`, `auth.login-link.used`, `backup.tenant.restore-divergence`, `bookkeeping.verification` and `mcp.tool.called`, and `AuditReason` has `service-account`, `tampered` and `diverged`.
- **Narrow the `method` of `HttpClientErrorRequestData` before reading it as an `HttpMethod`.** It is an `HttpClientMethod`, which names a method of WebDAV as well, such as `PROPFIND`, see [outgoing requests](#outgoing-requests).

### Generating and upgrading a project
- **A generated project builds with TypeScript 6.** `zi new` installs `typescript@^6.0.2`, the version Angular installs as well, so a workspace with both builds every project with one version. Before, the build of the api took whichever version the root of the workspace held. `zi upgrade` leaves the version of a project as it is: raise `typescript` in its `package.json` to `^6.0.2` yourself. The compiler options of `zibri/tsconfig.application.json` build with both versions.
- **A generated project reads its variables through one typed object.** `env` of `src/env.ts`, typed by `Env`, has a property for each variable `.env.example` lists, grouped where they belong together: `env.baseUrl`, `env.db.host`, `env.jwt.accessSecret`, `env.smtp.port`. `src/env.ts` is the one file that names a variable, so a mistyped name is a type error rather than an error once its line runs. Each property reads and checks its variable when it is used, with the same messages as before, so a command or a test that never sends a mail needs no `SMTP_HOST`. See [configuration](https://service-soft.github.io/zibri/operations/deployment/#configuration).

### Auth
- **Logging in with a link sent by email.** `LoginLinkAuthenticator`, listed in the `authenticators` of your application and of `AuthController`, adds `POST /auth/request-login-link`, which takes `{ email }` and answers `204` whether or not the email has an account, in the same time, on the budget of the auth routes per caller and on one per email. A deactivated user gets no link. The link opens the page of `loginLinkUrl` of `ZIBRI_DI_TOKENS.LOGIN_LINK_OPTIONS` with the token as its last segment, the tenant of the request put in by `resolveTenantUrl`, in the mail `loginLinkEmail`, both required, and works for `tokenExpiresInMs`, 15 minutes by default. The page posts the token to `POST /auth/login?authenticator=login-link` as `{ token }`, which logs in once and marks the email verified. Declare `LoginLinkToken`. A login by a link asks for a second factor as `twoFactorAtLogin` says, or with `secondFactor: 'none'` never, and codes by email do not count as its second factor: a user whose only one they are counts as a user without one. It does not count as a recent login for `@Auth.require2fa({ reauth })`, except for a user with neither a password nor a second factor when they log in, whom a route answers "Ask for a new login link, and log in with it to access this route." once their login is too old. `ReauthenticationRequiredError` takes the message as an optional second argument. With `bindToBrowser: true`, a link works only in the browser that asked for it, which gets a cookie. Recorded as `auth.login-link.requested` and `auth.login-link.used`. `zibri-contract` has `RequestLoginLinkInput` and `LoginLinkCredentials`. See [logging in with a link](https://service-soft.github.io/zibri/auth/login-links/).
- **The ways of logging in, for a frontend.** `GET /auth/login-methods`, which `loginMethodsRoute: true` of `AuthController` adds, answers `LoginMethods`, `{ password, loginLink }`, from the authenticators of the controller. Off by default, as an application can have a route of its own at that path. `zi new` writes the auth controller with it. `zibri-contract` has `LoginMethods`.
- **Invitations without a password.** `invite` with `withoutPassword: true` creates an account without a password, and needs `LoginLinkAuthenticator` among the authenticators, answering `400` otherwise. `POST /auth/accept-invitation` takes no password for it and logs the new user in by the link, answering what the login route answers, with `?strategy=` naming the strategy when there are several. `InvitationTokenValidity` answers `withoutPassword`, in `zibri-contract` too, optional in both until 4.0 so that a `resolveTokenValidity` of your own needs none, undefined meaning `false`, and `acceptForLogin` of `InvitationServiceInterface`, optional, answers the account to log in. The invitation entity has a nullable `withoutPassword`, which a Postgres data source with `schemaManagement: 'migrations'` adds itself. See [accepting without a password](https://service-soft.github.io/zibri/auth/invitations/#accepting-without-a-password).
- **What a login says of itself.** `Authentication` has `completesWithoutSecondFactor`, `excludedTwoFactorMethods` and `countsAsRecentLogin`. `JwtAuthStrategy` and `CookieAuthStrategy` keep `countsAsRecentLogin` for the whole login, in the nullable columns of `JwtRefreshToken` and `CookieAuthRefreshSession`, and `LoginTicket` keeps `excludedTwoFactorMethods` and `countsAsRecentLogin` of a login waiting for its second factor, which a login with `completesWithoutSecondFactor` does not. A Postgres data source with `schemaManagement: 'migrations'` adds the columns itself, see [data](#data) for `'external'`. A login strategy of your own answers no time from `resolveAuthenticatedAt` for a login whose `countsAsRecentLogin` is false.
- **Logging a websocket connection in from a browser.** The handshake takes the `authorization` and the tenant header from the `headers` of its `auth` as well, `{ auth: { headers: { authorization: 'Bearer ...' } } }`, which a browser sends with a connection that is a websocket from the start, where it sends no headers. A header the handshake carries itself is taken over the one of `auth`, the credential is checked again with it at its expiry and when logins end, and `headers` that are not an object of strings refuse the connection with a `400`. A token bound to a DPoP key logs no connection in. A `SocketIOWebsocketConnection` takes the request of its handshake as an optional fourth parameter, and one created without it reads the headers and the query of its handshake alone. See [logins](https://service-soft.github.io/zibri/endpoints/websocket/#logins).
- **Service accounts as a kind of user.** `BaseUser` has `kind`, a `UserKind` of `'person'` or `'service'`, `'person'` by default, which a write changing it for a stored user is refused with a `400`. `createServiceAccount` of `ZIBRI_DI_TOKENS.USER_SERVICE` creates a service account in the user entity you name, with its platform roles, no password and the email `<name>@service-accounts.invalid`. A service account acts through its API keys and the access tokens of the authorization server alone: logging in by any authenticator, `setPassword`, linking a passkey or an identity, a route taking a second factor, `invite` and accepting an invitation refuse it with a `403` and the new `ServiceAccountRefusedError`, and a password reset or a login link asked for its email mails nothing. `UserKindUtilities.validatePerson` refuses one in code of your own. `ApiKey` has `userKind`, which `findApiKeys` answers, and an audit entry has `userKind` where it knows it, for a refused login, a key created, a token issued and a refused request, with the new reason `service-account`. A `UserServiceInterface` of your own implements `createServiceAccount`, which is optional until 4.0. `GET /me` answers the `kind` of the user, in `CurrentUserProfile` of `zibri-contract` too, which has `UserKind`. `kind` is optional in both until 4.0, undefined meaning `'person'`, so that a profile a route of your own or a test of a frontend builds needs none. See [service accounts](https://service-soft.github.io/zibri/auth/api-keys/#service-accounts).
- **Managing service accounts through routes.** A controller of yours extending `ServiceAccountController`, naming the `userEntity` it creates service accounts in, lists every service account with `GET /`, by name, with its platform `roles`, its `tenantRoles` in the tenant of the request and its API keys, never with their secrets, creates one with `POST /` from its `name`, `roles` and `tenantRoles`, which it holds through a membership in the tenant of the request, sets its roles with `PUT /:serviceAccountId/roles`, creates a key with `POST /:serviceAccountId/api-keys` from its `name`, `permissions`, `tenantId`, `expiresAt` and `requireDpop`, answering the key itself once and taking a second factor or a recent login, revokes one with `DELETE /:serviceAccountId/api-keys/:apiKeyId`, and deletes a service account with `DELETE /:serviceAccountId`, revoking its keys first; the approval requests it proposed stay. Each role given or taken is checked as `assignRole` and `unassignRole` check it, and a role of the other level is refused with a `400`. The routes answer `404` for the id of a person. Listing is behind `service-accounts.read`, everything else behind `service-accounts.manage`: spread `ZIBRI_SERVICE_ACCOUNT_PLATFORM_PERMISSIONS` into your platform permissions. `findServiceAccounts` of the user service, optional until 4.0 like `deleteUser`, finds them, and a user service of your own without the two fails the start of an application registering the controller. `zibri-contract` has `ServiceAccountModel`, `ServiceAccountApiKeyModel`, `NewServiceAccountModel`, `ServiceAccountRolesModel`, `NewServiceAccountApiKeyModel`, `CreatedServiceAccountApiKeyModel`, `ZIBRI_SERVICE_ACCOUNT_LIMITS` and the permissions. See [letting administrators manage service accounts](https://service-soft.github.io/zibri/auth/api-keys/#letting-administrators-manage-service-accounts).
- **Upgrading the kind of users needs nothing of you, unless the schema is external.** A Postgres data source with `schemaManagement: 'migrations'` adds `kind` to your user tables and `userKind` to `ApiKey` itself, writing `'person'` into the rows stored before, and adds `userKind` and `approvalRequestId` to the audit entries. An audit entry stored before holds neither, and keeps the hash it was written with: a column a release added to an entity is left out of the hash of a row while it holds nothing. With `schemaManagement: 'external'`, see [data](#data).

### Plugins
- **Counting page views and visits.** `ZibriAnalyticsPlugin` counts the page views and events of your sites without a third party. Extend `AnalyticsController` with a `@Controller` of your own, declare `AnalyticsSite`, `AnalyticsPageViewRecord` and `AnalyticsEventRecord`, and provide `ZIBRI_ANALYTICS_PLUGIN_DI_TOKENS.OPTIONS_INPUT` with the `timezone` of the days. The sites counted are `AnalyticsSite` rows, each with a domain and a tenant or none: create those of your application with `createSite` of the analytics service, such as in your default data, which are verified at once. A site of a tenant is counted once it is verified by a DNS TXT record on its domain, `analytics-site-verification=<token>`, which the site routes answer and `POST /sites/:id/verify` reads through `ZIBRI_ANALYTICS_PLUGIN_DI_TOKENS.DNS_SERVICE`; several tenants may claim a domain, and one site at most verifies it. The record stays: `AnalyticsSiteVerificationCronJob` reads it daily, and a site whose record is missing for `verificationRecordGraceInMs`, 7 days by default, loses its verification until it is verified again with the same record. A site counts its domain with and without `www.`, in any case, and a site verified or removed takes effect from the next page view, on every instance within seconds. `POST /page-views` and `POST /events` are public, limited to 60 a minute per address by `AnalyticsRateLimiter`, bounded in every value, and drop a domain no verified site has, a site whose tenant is deactivated and a bot without saying so. A page view belongs to the tenant of its site, whatever tenant the request names. They keep the day, the page, the random id of the visit, the source of the visit, the random id of the visitor when they consented, and a rough operating system read from the `User-Agent`, never the address or the `User-Agent`. `GET /sites`, `POST /sites`, `POST /sites/:id/verify` and `DELETE /sites/:id` manage the sites, behind `analytics.sites.manage` for the sites of the tenant of the request, which always creates a site in that tenant, or `analytics.sites.manage_all` for every site. `GET /days`, `/pages`, `/sources`, `/systems` and `/funnel` answer the counts, each behind a tenant permission of `ZIBRI_ANALYTICS_PERMISSIONS`, for the sites of the tenant of the request, or a platform permission of `ZIBRI_ANALYTICS_PLATFORM_PERMISSIONS`, ending in `_all`, for every site; the funnel follows visits, or with `by=visitor` the visitors who consented across their visits. `AnalyticsCleanupCronJob` deletes the rows of every tenant after `retentionInMs`, two years by default. `zibri-contract` has the models, `AnalyticsOperatingSystem` and the permissions of both levels. See [counting page views and visits](https://service-soft.github.io/zibri/plugins/analytics-plugin/).
- **Approving actions.** `ZibriApprovalPlugin` lets a user, an API key or the application itself propose an action that a person approves before it runs. Extend `ApprovalRequestController` with a `@Controller` of your own, declare `ApprovalRequest` and `ApprovalDecision` in one data source, beside `ChainAnchor`, and register each `ApprovalAction` with `provideApprovalAction`, in the providers of your application or of a plugin. An action names its `input` model, the `permission` to approve it, the `proposePermission` to propose it, a `describe` answering a summary and the rows it writes, and a `run`. `POST /` or `propose` of `ZIBRI_APPROVAL_PLUGIN_DI_TOKENS.APPROVAL_REQUEST_SERVICE` validates the input and stores the request with its summary, the values it changes against the stored rows and a hash of each row; `propose` with a `system` proposes without a user. `POST /:id/approve` runs the action once, as the approver, in a transaction that records the decision with what the action answered, and `POST /:id/reject` records a note. Approving is refused to the user who proposed the request, refused with a `409` once a row it was proposed against changed, takes a second factor where the action sets `require2fa`, and runs the action once when two approve at the same moment. An action that throws leaves the request `FAILED`, keeping nothing it wrote. A policy of the action approves a request on its own once it is proposed, recorded as the one that decided it. A request expires after the `expiresInMs` of its action, 7 days by default, and `ApprovalRequestExpiryCronJob` closes it as `EXPIRED`. The decisions of each tenant form a hash chain the chain service checks. `eventNames` of the options emits a request proposed and decided as events of yours. `GET /` and `GET /:id` read the requests, behind `approval-requests.read`, and deciding takes `approval-requests.decide` and the permission of the action. `zibri-contract` has the models, the enums and `ZIBRI_APPROVAL_PERMISSIONS`. `AlsUtilities.runOutsideRequest` runs a function outside the request it is called in. See [approving actions](https://service-soft.github.io/zibri/plugins/approval-plugin/).
- **An MCP server for AI assistants.** `ZibriMcpPlugin`, created with the `allowedOrigins` a browser may call from and the `rateLimit` of each caller, serves the tools of your application over the Streamable HTTP transport of the Model Context Protocol, answering each message with JSON, in the revisions `2026-07-28` and, with `initialize`, `2025-11-25` and `2025-06-18`. Extend `McpController` with a `@Controller` of your own, and register each tool with `provideMcpTool`: an `McpReadTool` with its `input` and `output` models, a `permission` and `read`, or an `McpWriteTool` of an approval action, whose call proposes the action and answers the approval request as an `McpProposal`. Only a service account calls the endpoint, with an API key or an access token; it sees and calls the tools whose permission its credential carries in the tenant of the request, and a request from another origin is refused with a `403`. Arguments are validated against the model and answered as an error of the tool when they do not fit, and a client is given the JSON Schema of both models. Every call is recorded as `mcp.tool.called`, with the `approvalRequestId` a write tool proposed. A controller of yours extending `ServiceAccountMcpToolController` answers the tools a service account can use with `GET /:serviceAccountId`, those whose permission its roles carry in the tenant of the request, each as an `McpToolSummary`, behind `service-accounts.read`; `zibri-contract` has `McpToolSummaryModel`. See [serving AI assistants over MCP](https://service-soft.github.io/zibri/plugins/mcp-plugin/).
- **Importing bank statements.** `ZibriBankPlugin` imports the statements of the bank accounts of a tenant from CAMT.053 files of the versions `camt.053.001.02` and `camt.053.001.08`. Extend `BankController` with a `@Controller` of your own, declare `BankAccount`, `BankStatement` and `BankTransaction` beside what an archived entity needs, and register a file store named `bank-statements`, `BANK_STATEMENT_FILE_STORE_NAME`, or the one `store` of the options names. `POST /accounts` adds an account of an IBAN, `POST /statements` imports a file taken as a multipart body, and `importStatements` of `ZIBRI_BANK_PLUGIN_DI_TOKENS.BANK_STATEMENT_SERVICE` imports one from your code, in the transaction you pass. A file can hold several statements, of several accounts, and is imported whole or not at all. Each `BankStatement` keeps its period, its opening and closing balance and its original file, archived for `retention` of the options, 8 years from the end of its year by default: a bank statement is a booking document, which § 147 AO keeps for 8 years since the Bürokratieentlastungsgesetz IV of 2025. Each booked `BankTransaction` is stored once, told apart by the reference of the bank or a hash of what it holds, so the same file twice or files that overlap store it once; pending entries are left out. A file of an IBAN the tenant has no account of is refused with a `409` naming it, and so is a statement that does not continue from the closing balance of the one imported before it, until the missing statement is imported. A file that is not one of the two versions, or whose entries do not add up to its balances, is refused with a `400`. `GET /accounts`, `GET /statements` and `GET /transactions` list them. The routes are behind `ZIBRI_BANK_PERMISSIONS`: `bank.accounts.manage`, `bank.statements.import` and `bank.transactions.read`. `zibri-contract` has the models, `ArchivedFileModel` and the permissions. See [importing bank statements](https://service-soft.github.io/zibri/plugins/bank-plugin/).
- **Matching bank transactions with invoices.** With `matching` of the bank plugin options, beside `ZibriApprovalPlugin`, `ZibriInvoicingPlugin` and `BankMatch` in the data source of `ApprovalRequest`, the bank plugin suggests the invoices the money received pays once an import is committed. Each suggestion is an approval request of the action `bank.match`, `BankMatchApprovalAction`, proposed by the system `bank-matching`, with a `confidence` from 0 to 1 and its `reasons`: the invoice number in the remittance information or end-to-end id adds 0.6, the amount left of the transaction being the amount left of the invoice 0.25, and the payer having the name of the recipient, or its account having paid an invoice of the recipient before, 0.15; below 0.4 nothing is suggested. A suggestion matches what is left of the transaction or the invoice, whichever is less, so one transaction paying two invoices and two transactions paying one get a suggestion each. A person with `bank.matches.confirm` approves one, which records a `BankMatch` of the transaction, the `targetType` and `targetId` and the amount; approving checks what is left on both sides again, one match of a tenant at a time, and leaves a request above it `FAILED`. `paymentDifferenceTolerance` of `matching`, required, is the most of an invoice a match may leave open for the invoice to count as paid: the match records the rest as its `difference`, and above it the rest stays open. `autoApproveConfidence` of `matching` approves the suggestions of the system of at least that confidence through the policy `confidence-at-least-<confidence>`, none by default, and never a match of an account. Matchers of other targets, `BankMatcherInterface` providers of `BANK_MATCHER_DI_VARIANT`, suggest what the invoices leave, of money received or paid, such as the `EXPENSE` and `ACCOUNT` targets of the bookkeeping plugin, and postings, `BankMatchPostingInterface` providers of `BANK_MATCH_POSTING_DI_VARIANT`, book each match in the transaction it is written in. `POST /matches/:id/reversal` and `reverseMatch` reverse a match by one of the negative amount, once. Without `matching`, a proposal of `bank.match` is refused with a `409`. `POST /matches/suggestions` and `suggestMatches` of `ZIBRI_BANK_PLUGIN_DI_TOKENS.BANK_MATCH_SERVICE` suggest again for what is not matched in full, leaving out pairs pending or rejected, and `GET /matches` lists the matches of a transaction or an invoice. `ZIBRI_BANK_PERMISSIONS` has `bank.matches.read`, `bank.matches.suggest` and `bank.matches.confirm`, and `zibri-contract` `BankMatchModel` and `BankMatchTargetType`. See [matching transactions with invoices](https://service-soft.github.io/zibri/plugins/bank-plugin/#matching-transactions-with-invoices).
- **Keeping the books.** `ZibriBookkeepingPlugin` keeps the books of a tenant by double-entry bookkeeping, a tenant being one company. Extend `BookkeepingController` with a `@Controller` of your own, declare `BookkeepingSettings`, `BookkeepingAccount`, `FiscalYear`, `JournalEntry`, `JournalEntryLine`, `PostingRuleSet`, `Expense` and `ExpenseReceipt` in one data source, beside what an archived entity needs, register a file store named `receipts`, `EXPENSE_RECEIPT_FILE_STORE_NAME`, and provide `ZIBRI_BOOKKEEPING_PLUGIN_DI_TOKENS.OPTIONS_INPUT` with `tenantsWithoutBooks`. A tenant keeps books once `POST /settings` or `createSettings` gave it its `BookkeepingSettings`, one row at most: the `currency`, the history of its `legalForms` and its `company`. `PATCH /settings` and `updateSettings` change them in one transaction, checked as a whole by the conformances of each legal form of the resulting history, each property unchanged when absent: the `currency` while there is no fiscal year, a `legalForm` appended to the history from after the end of the last closed fiscal year, and the `company` replaced whole, or removed with `null`. Its accounts, of the `BookkeepingAccountType` `ASSET`, `LIABILITY`, `EQUITY`, `REVENUE` or `EXPENSE`, are data your application seeds, none by default. Its fiscal years follow each other without overlapping or leaving a gap: the first names its start and ends with its calendar year by default, every later one starts the day after the one before and lasts a year by default. `post` of `ZIBRI_BOOKKEEPING_PLUGIN_DI_TOKENS.JOURNAL_SERVICE` and `POST /entries` post an entry of at least 2 lines whose debits add up to its credits, in the minor units of the currency, on open accounts of the books and into an open fiscal year, once per `sourceType` and `sourceId`, and refuse anything else with a message saying what it needs to be. Each entry is numbered with the next `sequence` of its fiscal year, drawn in the transaction of the entry, so one rolled back leaves no gap. An entry is never changed: `reverse` and `POST /entries/:id/reversal` post its mirror, once, and a reversal is not reversed. `closeFiscalYear` and `POST /fiscal-years/:id/closing` refuse every further posting into a year, carry its revenue and expenses into the equity account named, on a line of the `JournalEntryLineRole` `RESULT`, a role only the closing gives a line, carry each other account in the `resultPosition` of a full balance sheet, such as the allocation to the legal reserve in `equity-and-liabilities.A.V`, into it as well, and open the next year, created when missing, with the balances of the balance sheet accounts. `reopenFiscalYear` and `POST /fiscal-years/:id/reopening`, behind `bookkeeping.reopen-fiscal-year` and a second factor given again, reopen a closed year with a `reason` to correct its books, latest first: they reverse its closing entry and the opening entry of the next year, which closing it again posts anew, count the reopening in `reopenings` of the fiscal year, keep the statements of the closing before, each `FiscalYearStatement` numbered by its `closing`, and record `bookkeeping.fiscal-year.reopened` in the audit trail. A conformance refuses a reopening with `validateReopening`, such as `EBilanzConformanceService` for a year whose E-Bilanz is filed, unless it is reopened `forCorrection`. A closing or opening entry is reversed by a reopening alone: `reverse` and `POST /entries/:id/reversal` refuse one with a `409`. `JournalEntry` and `JournalEntryLine` are chained, each in a chain of its own per tenant, and archived for `retention` of the options, 10 years from the end of the calendar year the fiscal year ends in by default. `resolveVerification` and `GET /verification` check both chains and that every entry balances, naming the first entry or line that does not hold, and `BookkeepingVerificationCronJob` does so for every tenant once a day, recording each problem in the audit trail as `bookkeeping.verification` with the new `AuditReason.TAMPERED`. Rules of a law are `BookkeepingConformanceServiceInterface` services under `BOOKKEEPING_CONFORMANCE_SERVICES`, those of the HGB and the UG by default, which apply by the legal form of the tenant at the end of a fiscal year unless the year names its `conformances`: they propose entries at closing, which `GET /fiscal-years/:id/closing-proposals` answers, and can refuse the closing. The routes are behind `ZIBRI_BOOKKEEPING_PERMISSIONS`, `bookkeeping.read`, `bookkeeping.post`, `bookkeeping.close-fiscal-year`, `bookkeeping.reopen-fiscal-year`, `bookkeeping.manage` and `bookkeeping.expenses.manage`, or the `_all` of `ZIBRI_BOOKKEEPING_PLATFORM_PERMISSIONS` for the books of every tenant, named by `tenantId` in a request naming no tenant. `zibri-contract` has the models and the permissions. See [keeping the books](https://service-soft.github.io/zibri/plugins/bookkeeping-plugin/).

An `InvoiceNumberServiceInterface` of your own implements the optional `generateCreditNoteNumber` to create credit notes, and works as before without it. See [cancelling an invoice](https://service-soft.github.io/zibri/plugins/invoicing-plugin/#cancelling-an-invoice).
- **What of an invoice is paid.** `resolvePaymentState` of `ZIBRI_INVOICING_PLUGIN_DI_TOKENS.INVOICE_PAYMENT_SERVICE` answers the `total` of an invoice, what its credit notes credit, what is `paid` and `open`, and a `status` of `OPEN`, `PARTLY_PAID`, `PAID` or `CREDITED`, and `resolvePaymentStates` those of many invoices. What is paid comes from the payment sources, providers of `INVOICE_PAYMENT_SOURCE_DI_VARIANT` implementing `InvoicePaymentSourceInterface`, such as the bank plugin with `matching`. Without one, the state is undefined, and nothing else changes. See [reading what of an invoice is paid](https://service-soft.github.io/zibri/plugins/invoicing-plugin/#reading-what-of-an-invoice-is-paid).
- **Booking issued invoices.** A provider of `INVOICE_POSTING_DI_VARIANT` implementing `InvoicePostingInterface`, such as the bookkeeping plugin, is handed every invoice and credit note a write issues, before the write and in its transaction, and what it throws refuses the write. A write naming an `issuedAt` without a transaction runs in one of the data source of `Invoice`, started for it, so a write that fails posts nothing. Without a provider, issuing an invoice is as it was. See [booking issued invoices](https://service-soft.github.io/zibri/plugins/invoicing-plugin/#booking-issued-invoices).
- **Keeping issued invoices unchanged.** With `issuedInvoicesReadOnly` of the invoicing options, an invoice whose `issuedAt` is set can no longer be changed or deleted, and a credit note corrects it. It is `false` by default, and `true` from 4.0. See [keeping issued invoices unchanged](https://service-soft.github.io/zibri/plugins/invoicing-plugin/#keeping-issued-invoices-unchanged).
- **Number formats.** `numberFormat` of the invoicing options sets the format of invoice numbers, of `{year}`, `{yy}`, `{month}`, `{recipient}`, `{counter}` and any text between them, such as `{year}-{counter}` for one sequence a year, and `creditNoteNumberFormat` the one of credit notes, with `{invoice}`. The counter counts on its own for every distinct value of the rest of the format. The defaults draw the numbers of before, and the stored counters go on counting. `numberFormat` and `creditNoteNumberFormat` of the `CompanyInfo` of a tenant set its own. A format without `{counter}`, or with a token it does not know, stops the start. A name abbreviation is claimed only for a format with `{recipient}`. A class of yours extending `InvoiceNumberService` draws a number with `resolveCounter`, reads a temporary one with `resolveTemporaryCounter` and the moment numbered at with `resolveNumberingContext`, which answers a `NumberingContext`. The options this release adds are optional in `InvoicingOptions` until 4.0, with their defaults, so options written out whole for 3.2 stay valid. See [numbering invoices](https://service-soft.github.io/zibri/plugins/invoicing-plugin/#numbering-invoices).
- **Upgrading the counters of invoice numbers needs nothing of you, unless the schema is external.** `NumberInvoices` has a nullable `scope`, the rendered format, with a unique of its own beside the one on year and recipient, and the first start gives the stored counters their scope. A Postgres data source with `schemaManagement: 'migrations'` adds the columns of `Invoice` and `NumberInvoices` itself, so the application writes no migration. With `schemaManagement: 'external'`, see [data](#data). An instance of 3.2, beside this release during a rolling deploy or after going back to 3.2, draws the numbers of the default format from the same counters, by year and recipient. A counter of another format or of credit notes is kept under year 0 and its scope, so it never meets one of those. Going back is the one of a release that changed the uniques, see [going back](https://service-soft.github.io/zibri/data/data-source/#going-back).

### Localization
- **The framework's own messages in German.** An application that supports `de`, or a locale of it such as `de-AT`, answers validation errors, login errors and the other messages of the framework in German without translating them itself. The German is read before your `translations/de.xlf`, so a `<target>` you wrote for one of those strings keeps replacing it. See [providing translations](https://service-soft.github.io/zibri/templates/localization/#providing-translations).
- **Running work in a locale.** `runInLocale(locale, fn)` of the localize service runs a function in a locale: `$ts`, `$f`, the formatting methods and every template rendered inside it use it, after every `await` too, inside a request and outside one, such as in a cron job mailing each user in their language. A locale is matched to a supported one, so `de-AT` runs in `de`, and one that matches none, `null` and `undefined` run in the `defaultLocale`. Inside another, the inner locale applies. `CURRENT_LOCALE` of the request context stays the locale the request asks for. The function `runInLocale` calls it: `runInLocale` of `LocalizeServiceInterface` is optional until 4.0, and with a localize service of your own without it, the function runs as it is, in the locale your service resolves. See [running work in the locale of a user](https://service-soft.github.io/zibri/templates/localization/#running-work-in-the-locale-of-a-user).
- **The locale of a user.** `BaseUserEntity()` has a nullable `locale`, which a user created without one gets from the request creating them, from `runInLocale`, or else the `defaultLocale`. `updateLocale` of `UserServiceInterface` changes it, refusing a locale the application does not support with a `400`, and `GET /me` answers it. A user changes their own with `PATCH /me`, which `updateCurrentUserRoute: true` of `AuthController` adds, off by default as an application can have a `PATCH /me` of its own; `UpdateCurrentUserInput` of `zibri-contract` is what it takes. `zi new` writes the auth controller with it, and `zi upgrade` brings it into one it wrote. The invitation mail, the links verifying and changing an address, the password reset and the second factor codes by email and SMS are rendered in the locale of their recipient, subject included, and the logs the logger mails in the `defaultLocale`. An invitation keeps the `locale` it is sent in: the `locale` of `invite`, else the one of the account the email has, else the one of the request inviting. Its link sent again is in it, and the account it creates gets it, unless `POST /accept-invitation` names a `locale` of its own. With `schemaManagement: 'migrations'`, a Postgres data source adds the nullable `locale` columns to the tables of your user and invitation entities itself, and `zi migrate create` leaves them out. `zibri-contract` declares `LocaleCode`, and has the `locale` of `CurrentUserProfile`, `AcceptInvitationInput` and `Invitation`. See [the locale of a user](https://service-soft.github.io/zibri/templates/localization/#the-locale-of-a-user).
- **A price that keeps its currency in every language.** With `priceCurrency: 'defaultLocale'` of the localize options, `formatPrice` and the `$f.price` of a page format an amount without a `currency` in the currency of the `defaultLocale`, whichever locale formats it: with `en-US` the default and `de` supported, `formatPrice(19.99, { locale: 'de' })` is `19,99 $` rather than `19,99 €`. Without it, such an amount is in the currency of the locale formatting it, as before. The invoicing plugin, the reports of the bookkeeping plugin and the bank plugin name their currency. See [formatting](https://service-soft.github.io/zibri/templates/localization/#formatting).

### Documents
- **PDFs with pdfmake 0.3.** The optional peer `pdfmake` is `^0.2.23 || ^0.3.15`. `PdfUtilities.resolve` creates a pdf with either version and returns the same `PdfDocument`, and the invoicing plugin creates its pdfs with it. With 0.2 nothing changes. ### Files
- **File stores and a file service.** A file store keeps the bytes of files: `FsFileStore` in a folder, `S3FileStore` in a bucket of an S3 compatible storage, `SftpFileStore` on an SFTP server, or a class of your own implementing `FileStoreInterface`. Decorate it with `@FileStore()`, list it in `fileStores` of the application options, and declare `FileRecord` in your data source. `store` of the file service, `ZIBRI_DI_TOKENS.FILE_SERVICE`, keeps a file in a store by its name, as a row of `FileRecord` of the current tenant with its name, mime type, size, SHA-256, store, key, and when and by whom it was stored, in the transaction you pass. `read` and `readStream` refuse bytes that no longer match their SHA-256 with a `FileHashMismatchError` naming the file. Files of the same content in the same store and tenant share their bytes, which go with their last row. A stream is staged in `ZIBRI_DI_TOKENS.FILE_STAGING_FOLDER` while it is hashed, never held in memory whole. `FileCleanupCronJob` deletes the bytes no row references a day after they were written, such as those of a rolled back transaction. A tenant can keep its files in a store of its own, a bucket or an SFTP server, added with `createTenantFileStore` and stored in `TenantFileStore`, as it can its backups, reaching the hosts `ZIBRI_DI_TOKENS.FILE_TENANT_STORE_OPTIONS` allows. See [files](https://service-soft.github.io/zibri/data/files/).
- **`S3StorageOptions` and `SftpStorageOptions`** are the options of a bucket and of an SFTP server, which `S3FileStore` and `SftpFileStore` take. `S3BackupTransportOptions` and `SftpBackupTransportOptions` are the same types under their names, and every transport takes what it took.
- **The files of an entity in a file store.** `@Property.file({ store: 'documents', ... })` keeps the file of an entity in that store through the file service, and the column holds the id of its `FileRecord`; `@Property.array({ items: { type: 'file', store: 'documents', ... } })` holds a list of ids. `store` also takes a DI token whose value is the name, read once the providers of the application exist and checked when it starts, so that an application decides the store of an entity a plugin declares. A response answers a `FileReference` in place of each id, `{ name, mimeType, size, url }`, read when it is written, every file of a page in one go. Its `url` is the download route of the first `CrudController` of the entity, `GET /<route>/:id/files/<property>` and `<property>.<index>` for an item of an array, below the `baseUrl` and with the tenant of the request, or `null` for an entity no `CrudController` serves. The route has the access rules of `findById` and streams the bytes through `readStream`, with their mime type and as a download under their name. `POST` and `PATCH` of such a controller take a multipart body: a file part replaces the file, an empty field removes it, and a `PATCH` leaving the property out keeps it. The files are stored in the transaction of the row. The repository owns the files of its rows, on every data source: once a write is committed, the files an update replaces or removes are deleted through `deleteRemovedFiles` of the file service, and so is every file of a row deleted, by `deleteById`, `deleteAll`, `hardDelete: true` or a relation that cascades removes. A soft delete keeps them for its restore, and a write rolled back keeps them. See [deleting the files of a row](https://service-soft.github.io/zibri/data/files/#deleting-the-files-of-a-row). A file in a store inside an object, or in a store that is not registered, is refused at start, and so is such a controller whose bodies hold a file the entity keeps in its column. The OpenAPI document describes such a property as uploaded bytes and answered as a `FileReference`. A file property without a `store` keeps the bytes in its column, as before. `findFiles` of `FileServiceInterface` reads several files at once, and `deleteRemovedFiles` deletes the files a write took off its rows. `zibri-contract` has `FileReference`. See [keeping the files of an entity in a file store](https://service-soft.github.io/zibri/data/files/#keeping-the-files-of-an-entity-in-a-file-store).
- **Backing up a file store.** A file store marked with `@Backup({ transports, encrypt })` beside `@FileStore()` is a backup resource of its own: a backup holds the bytes of every file a row of `FileRecord` names in it, each content once, through the chunks of the backup, so a backup after another adds the files stored since. Within a backup it is stored once the data source holding `FileRecord` is. A restore of both puts back the rows and the bytes, a restore puts back bytes only once they match the SHA-256 their key names and deletes none, and it keeps no copy of the store to put back. After a restore of the rows or of the store, alone or together, the application warns about the files whose bytes the store lacks, naming them and the store to restore them from. A backup of a tenant holds the bytes of the tenant's files, and a restore of it puts back those alone; the files of a tenant's own store are not backed up. Nothing changes for a store without `@Backup`: its rows are backed up with their data source, and its bytes are not. See [backing up a file store](https://service-soft.github.io/zibri/data/files/#backing-up-a-file-store).
- **Archiving documents.** `@Archive({ retention })` on an entity declared with `@Entity({ chained: true })` and extending `BaseArchivedEntity`, a type of document such as a receipt, keeps its rows and their files unchanged for their retention, on every data source and through every write path. When a row is created, the repository fills in `retainUntil`, counted in whole years, months and days from the end of the calendar year of the row's date, as § 147 AO counts it, or with `from: 'date'` from the date itself, on the calendar of the `defaultTimezone`. The date is the `dateProperty` the archive names, or when the row is created. A row created with a `retainUntil` of its own keeps it. An update is refused with a `409`, and a delete before `retainUntil` with an `ArchiveRetentionError`, a `409` naming the row and its `retainUntil`; after it, `deleteById` and `deleteAll` delete the row with its files. `archivedFiles` records the SHA-256 of each file the row holds, which its hash chain covers, and with `copies: ['offsite']` the ids of a copy of each file in each store named, made in the transaction of the row. `ZIBRI_DI_TOKENS.ARCHIVE_SERVICE` checks the chains and reads every file and copy with `resolveVerification`, naming each file that is missing, changed or unreadable, finds the rows whose retention ended with `findDue`, deletes them with their files and copies with `prune`, and reads a file from the first copy whose bytes match with `readFile`, which the download route of a `CrudController` uses for an archived entity. `ArchivePruneCronJob` prunes once a day when you list it in `cronJobs`. A row deleted from inside its chain is recorded in `ChainGap`, which the data source of an archived entity declares, and which checking a chain steps over; `recordRemovedRows` of `ChainServiceInterface` records it, optional for a chain service of your own and needed by the archive. `copy` of `FileServiceInterface` copies a file into another store, and `findFiles` takes a transaction. Nothing changes for an entity without `@Archive`. See [archiving documents](https://service-soft.github.io/zibri/data/archive/).

### Data
- **The columns of the framework in a schema of your own.** A Postgres data source with `schemaManagement: 'external'` adds none of the columns this release adds to the entities of the framework, and a schema of 3.2 runs unchanged: on every start it finds the ones the database lacks, reads and writes the rows without them, and warns once, listing them by table with the statements that add them, the backfills of `'person'` and `'INVOICE'` and the unique of `NumberInvoices` on `tenantId` and `scope` included. Without them, a user is a person, an invoice is an invoice that no final number issues, and a counter of invoice numbers counts by year and recipient. The features needing one throw a `MissingFrameworkColumnError` naming the columns and the statements: a service account, the locale of a user and of an invitation, an invitation without a password or sharing rows, a login by a link that is no recent one, a mail with a `replyTo`, an audit entry of an approval, credit notes, `issuedInvoicesReadOnly`, booking or archiving issued invoices, a `numberFormat` of your own, and a filter on such a column. A start finding them uses them. `FrameworkColumnUtilities.hasColumns` tells code of your own whether a table has them. The columns are `locale` and `kind` of your user entities, `locale`, `withoutPassword` and `rowShares` of your invitation entities, `excludedTwoFactorMethods` and `countsAsRecentLogin` of `LoginTicket`, `countsAsRecentLogin` of `JwtRefreshToken` and `CookieAuthRefreshSession`, `userKind` of `ApiKey`, `userKind` and `approvalRequestId` of `AuditEntry` and `ChainedAuditEntry`, `replyTo` of `Email`, `type`, `precedingInvoices` and `issuedAt` of `Invoice`, and `scope` of `NumberInvoices`. The hash of a chained row leaves out a value of such a column that says what a row without it says, such as the `userKind` `'person'`, so a row stored without the column verifies. See [the columns of the framework in a schema of your own](https://service-soft.github.io/zibri/data/data-source/#the-columns-of-the-framework-in-a-schema-of-your-own).
- **Escaping a search term.** `FilterUtilities.escapeLike` escapes the `%`, `_` and backslashes of a text, so that an `iLike` between two `%` finds the values containing it as it is written. See [filtering and ordering a list](https://service-soft.github.io/zibri/endpoints/creating-endpoints/#filtering-and-ordering-a-list).
- **Observing writes.** A write observer sees every write to the rows of an entity, however a repository gets to it. Implement `EntityWriteObserver` and register it with `register` of `EntityWriteObserverRegistry` from `onAppInit` or `afterAppInit`; registering later throws. `validateWrite` refuses a write before anything is written, in its transaction, and reads what it does to each row with `resolveRowWrites`. `completeWrite` writes the rows that belong with the rows a write made, in its transaction and with their ids, and what it throws fails the write. `handleWritten` follows a write once it is committed, with the rows `before` and `after` it. An observer whose `requiresTransaction` answers true for a write without a transaction has the write run, with every observer of the entity, in a transaction of the data source of the entity, started for it and committed once the write is complete; every other write runs as it is called. `EntityWrite`, `ObservedWrite`, `MadeWrite`, `WrittenRows`, `RowWrite` and `WriteOperation` are the types an observer is handed. See [observing writes](https://service-soft.github.io/zibri/data/write-observers/).
- **Sharing rows with selected people.** `@Entity({ shareable: { fullAccess, parent, roles } })` narrows every repository call on an entity, like a scope and beside its own, for a member whose roles do not carry `fullAccess`: they see the rows shared with them and the rows below those through `parent`, a relation of the entity to itself, to any depth. A write placing a row below itself is refused with a `400`. `@Entity({ sharedThrough: '<relation>' })` narrows an entity to the rows belonging to a row seen, through as many entities as declare it. The new `RowShare`, which your data source declares beside a shareable entity, keeps the shares, and is deleted with its row and its user. `ZIBRI_DI_TOKENS.SHARE_SERVICE` shares and unshares a row in a role the entity declares, answers the highest role along the rows above a row with `resolveRole`, and shares by email with `shareByEmail`, inviting an email without a membership with the guest roles you name and creating the share once it is accepted. `invite` takes the rows to share as `rowShares`, which `BaseInvitationEntity()` keeps in a nullable column of the same name, added to a table that lacks it without a migration of yours. `@Auth.requireShareRole(entity, role, pathParam)` and `validateRole` let a caller through with `fullAccess` or the role on the row, answering `404` for a row they do not see and `403` for a lower role. `zibri-contract` has `RowShareModel`, `PendingRowShareModel` and `SharedUserModel`, the one a guest reads other users as. See [sharing rows with selected people](https://service-soft.github.io/zibri/data/sharing/).
- **Backups on a WebDAV server and on Nextcloud.** `WebDavBackupTransport` stores backups in a `folder` of a WebDAV server: each key a file, uploaded under a name of its own beside it and moved onto it once whole, so an upload that fails leaves no key behind, and each folder listed one level at a time. An upload a process left behind when it ended before the move is deleted by the garbage collection once a day has passed since it was written, with the folders it alone kept, through `deleteAbandonedUploads`, an optional member of `BackupTransportSessionInterface` each collection calls once while no resource is being stored. Its `network` is required, `undefined` for a server of your own, and a request waits five minutes and is attempted 3 times by default. `NextcloudBackupTransport` stores them in a folder of a Nextcloud the same way, logged in as a user owning the folder, and keeps the folder read-only for everyone else: before a session writes, a share with a user or a group allowing more than reading is made read-only again, a share by link, by email or with another server is deleted, both logged as an error, a share to read of someone `sharedWith` does not name is left and warned about, and the users and groups of the required `sharedWith` get a share to read. What it deletes it deletes from the trash bin of Nextcloud too, an upload left behind included, so the garbage collection frees the space. Tenants keep backups through their WebDAV connections with `WebDavTenantBackupTransportKind` (`'web-dav'`) and `NextcloudTenantBackupTransportKind` (`'nextcloud'`), which you list in `kinds` of `ZIBRI_DI_TOKENS.BACKUP_TENANT_TRANSPORT_OPTIONS`: their settings name the `connectionId` of a `TenantWebDavConnection` of the matching kind and the `folder`, their secret is `{}`, and `WebDavBackupTransportUsageFinder`, registered for you as `ZIBRI_DI_TOKENS.BACKUP_WEB_DAV_CONNECTION_USAGE_FINDER`, keeps a connection from being deleted while a transport is kept through it. `createTransport` of a `TenantBackupTransportKindInterface` is called with the id of the tenant as well. See [storing backups on a WebDAV server](https://service-soft.github.io/zibri/data/backup/#storing-backups-on-a-webdav-server) and [on Nextcloud](https://service-soft.github.io/zibri/data/backup/#storing-backups-on-nextcloud).
- **Tenants managing their backup transports.** A controller of yours extending `TenantBackupTransportController` lists the transports of the tenant with `GET /`, by name and never with their secrets, the kinds it may add with `GET /kinds`, adds one with `POST /` once a small object was written to it and deleted, changes the `name`, `settings` or `secret` of one with `PATCH /:transportId`, testing changed settings or a changed secret the same way, and deletes one with `DELETE /:transportId`, for every kind `kinds` of `ZIBRI_DI_TOKENS.BACKUP_TENANT_TRANSPORT_OPTIONS` lists, one of your own included. The settings of a transport a backup is stored on are refused with a `409` naming the backups, as deleting it is, while its name and secret change at any time. `updateTenantBackupTransport` of the backup service, optional until 4.0, makes the change, and `findTenantBackupTransports` answers the transports by name. A backup service of your own without the four methods the routes call fails the start of an application registering the controller. A transport whose row another instance changed is reached with the row as it is now. Spread `ZIBRI_BACKUP_TRANSPORT_PERMISSIONS` (`backup-transports.read`, `backup-transports.manage`) into yours. `zibri-contract` has `TenantBackupTransportModel`, `NewTenantBackupTransportModel`, `TenantBackupTransportChangeModel`, `TenantBackupTransportKindModel`, `ZIBRI_BACKUP_TRANSPORT_LIMITS`, the names of the kinds Zibri ships in `ZIBRI_BACKUP_TRANSPORT_KINDS`, and their settings and secrets, such as `TenantSftpTransportSettingsModel` and `TenantSftpTransportSecretModel`. See [letting tenants manage their transports](https://service-soft.github.io/zibri/data/backup/#letting-tenants-manage-their-transports).

### Outgoing requests
- **A WebDAV client.** `WebDavClient` reads and writes the files and folders of a folder on a WebDAV server, such as Nextcloud, through the http client, logged in with the `username` and `password` of a `WebDavConnection`: `get` reads a file as a stream with its ETag, `put` writes text, bytes or the chunks of an `HttpClientBufferedBody` under exactly one of `ifMatch`, `ifNoneMatch: '*'` and `overwrite: true` and returns its ETag, `delete`, `move` with a required `overwrite`, `createFolder` with the folders above it, `findEntries` lists one level of a folder and `findEntry` finds one path, each with further properties a listing asks for by namespace and name. A refusal throws a `WebDavNotFoundError`, `WebDavPreconditionFailedError`, `WebDavConflictError` or `WebDavForbiddenError`, each an `HttpClientError`. `TenantWebDavConnection`, an entity whose password is stored encrypted, is a folder a tenant connects to, and `WebDavClient.createForTenant` reaches it at public addresses over https only, as `ZIBRI_DI_TOKENS.WEB_DAV_TENANT_CONNECTION_OPTIONS` says. A class extending the client sends requests of its own with `resolveRequestOptions`, reads a multistatus answer with `resolveEntries`, and checks the hosts of a tenant's connection with `resolveTenantNetwork`. See [WebDAV](https://service-soft.github.io/zibri/endpoints/web-dav/).
- **A Nextcloud client.** `NextcloudClient` is a `WebDavClient` of a url below `/remote.php/dav/` that finds a file by the id Nextcloud keeps it under when it is renamed or moved, `NextcloudClient.FILE_ID_PROPERTY`, with `findEntryByFileId`, a `SEARCH` of the files of its user. `createShare` shares a file or a folder through the share api of Nextcloud, by a link to read, with a required `password` and `expiresOn`, or with a `'user'` or a `'group'`, with required `permissions`. `findShare` finds a share by its id, `undefined` once it is deleted, `findShares` every share of a path, `updateShare` changes what a share permits, and `deleteShare` deletes one, a share already gone counting as deleted. `findTrashBinEntries` finds what the trash bin of the user holds that was deleted from within a folder, each a `NextcloudTrashBinEntry` naming where it was, and `deleteTrashBinEntry` deletes one for good. `NextcloudClient.createForTenant` checks the hosts of a tenant's connection, and a class extending it reaches the OCS api with `resolveOcsUrl`. See [Nextcloud](https://service-soft.github.io/zibri/endpoints/nextcloud/).
- **Mirroring files into a folder.** `mirrorFile` of `ZIBRI_DI_TOKENS.FILE_MIRROR_SERVICE` queues a `FileToMirror`, such as the pdf of an invoice at `Customers/<name>/Invoices/<number>.pdf`, in the transaction it is handed, and `FileMirrorCronJob`, registered for you once the data source declares `FileMirrorRequest` and `MirroredFile`, writes it into the folder of a `TenantWebDavConnection` once the transaction is committed, with the folders it is in, retried 14 times over some six days. The same content again writes nothing. A file is created under `If-None-Match: *` and written again under `If-Match` of the ETag written last, so a file somebody changed in the folder is left as it is, its `MirroredFile` recording the conflict `CHANGED` and a warning logged; `findConflicts` finds a page of them. Nothing is deleted. A file somebody moved is `MISSING` through a connection of the kind `WEB_DAV`, and found again by its id and written where it is through one of the kind `NEXTCLOUD`. The newest version of a file in conflict is kept, and `resolveConflict` writes it over what is in the folder with `MirroredFileConflictResolution.OVERWRITE`, where the id says the file is now or where it was mirrored to once it is gone, or forgets the file with `STOP_MIRRORING`, after which a version mirrored to its path is a new file. `resolveShareLink` answers a link of a folder or a file of a Nextcloud to read, the same one while Nextcloud has it, as a `FileMirrorShareLink`, and `revokeShareLink` deletes its share in Nextcloud and then the link. `FileMirrorUsageCleaner` removes the rows of a connection that is deleted. An application switches it on with `renderAtRuntime` of `ZIBRI_DI_TOKENS.MARKDOWN_OPTIONS` and lists `zibri-mdx` in its dependencies, which it checks for while it starts. `MarkdownService`, replaceable through `ZIBRI_DI_TOKENS.MARKDOWN_SERVICE`, resolves the page. See [rendering markdown at runtime](https://service-soft.github.io/zibri/templates/templating/#rendering-markdown-at-runtime).
- **The rest of MJML's components.** `MjHero`, `MjTable`, `MjNavbar`, `MjSocial`, `MjCarousel` and `MjAccordion` with their parts, and in the head `MjBreakpoint`, `MjFont` and `MjHtmlAttributes`, which needs the package `cheerio`. Each nests where MJML lets it. See [rendering an email](https://service-soft.github.io/zibri/templates/templating/#rendering-an-email).
- **The nesting of an email follows your own components.** What a component renders is checked against the parent its use sits in, and what you pass it, its children or another prop, against where it places them. The build follows a component of another file to the file that declares it. Such a mistake is a `ZTSX004` warning, and fails the build from 4.0. See [nesting is checked at compile time](https://service-soft.github.io/zibri/templates/templating/#nesting-is-checked-at-compile-time).
- `renderPage` of `zibri-tsx` takes `contexts`, values of contexts for every component of the page.
- `TsxUtilities.renderPage` renders a page whose props are all optional without them.

### Endpoints
- **Filtering and ordering the list of a `CrudController`.** `findAll` takes an `order`, nested like the entity, `?order={"dueAt":"ASC","address":{"city":"DESC"}}`, by every string, number, boolean and date that is not excluded, encrypted, hashed or a password, in the entity and the objects inside it. An `OrderConfig` as `order` in the options names the properties, and reaches into a relation to one row. `order: false` takes none. A `FilterConfig` as `filter` in the options makes it take a `filter`, `?filter={"title":"invoice","project":{"name":"Website"}}`: it says for each property whether it matches by `'equals'`, `'iLike'`, `'fuzzy'`, `'oneOf'`, `'range'` or `'includes'`, and filters an object, the items of an array and a related row by the properties inside. Both are validated against the entity while the application starts, and each request against them. `FilterUtilities.resolveWhere` turns a filter into the where of a repository for a route of your own. See [filtering and ordering a list](https://service-soft.github.io/zibri/endpoints/creating-endpoints/#filtering-and-ordering-a-list).
- **An order reaches into an object property**, `order: { address: { city: 'ASC' } }`, on every data source, and sorts each value the way a property of its type on the entity sorts. See [filtering inside an object property](https://service-soft.github.io/zibri/data/data-source/#filtering-inside-an-object-property).
- **A `regex` needs no package of its own.** A declared `regex` runs in time linear to the value without `re2`, which a project can remove from its `dependencies` and its `allowScripts`. It matches what the same `RegExp` matches, where `re2` differed from it in places. With the `v` flag, a class matching strings of several characters, such as `[\q{abc}]`, is refused while the application starts. See [models](https://service-soft.github.io/zibri/data/models/).
- **The new package `zibri-contract`** holds the models a frontend shares with zibri, as they arrive as json, without the rest of the framework: the types of a filter and an order, `FilterConfig`, `FilterValue`, `OrderConfig` and `OrderValue`, which `zibri` exports as well, and `PaginationResult`, `ErrorResponseBody`, what the auth routes answer and take, logs and change sets. `LogLevel` and `ChangeSetType` of `zibri` are the enums of `zibri-contract`, and a check of the typecheck holds the models of `zibri` to the ones there.

### Application
- **A start waits for no index that only makes reads faster.** On Postgres, an index that is no unique, declared or kept for a relation or a search, is built once the application started, by one instance at a time under a lock of its own, and logged at `info` once built. On a large table a build takes minutes, which a start spent unable to answer, and an orchestrator restarting the instance as unresponsive cut short again and again. Uniques and checks are in place before the start is done, as before. A build the application is shut down during is built again by the next start. `PostgresDataSource.waitForIndexBuilds()` waits for them, which `startTestServer` of `zibri-testing` does after every start. See [keeping indexes and uniques](https://service-soft.github.io/zibri/data/data-source/#keeping-indexes-and-uniques).
- **A log names its application.** `Log` has an `application`, the `name` of the application options, so the logs of several applications in one table, like the ones a frontend sends to a route of yours, tell apart. A log written while no application runs has none. With `schemaManagement: 'migrations'`, the data source adds the column itself, see [upgrading from 3.0](#upgrading-from-30).
- **`stackTraceLimit`** says how many frames a stack trace keeps, in the process and in its thread jobs. It defaults to 50, which reaches your own code from inside a write to a data source, and a process started with another limit than node's 10, such as with `--stack-trace-limit`, keeps it. See [choosing how much of a stack trace to keep](https://service-soft.github.io/zibri/application/app-settings/#choosing-how-much-of-a-stack-trace-to-keep).
- A deployment carries none of what only building the application uses: `zibri` no longer names `typescript`, `ts-node`, `webpack`, `copy-webpack-plugin` and `mini-css-extract-plugin` as peers, and uses the application's own. A deployment pruned of its devDependencies had kept them, more than 40 MB. A deployment running TypeScript worker files with `enableTsWorkerFiles` lists `ts-node` and `typescript` in its `dependencies`. See [running TypeScript worker files](https://service-soft.github.io/zibri/background-work/multithreading/#running-typescript-worker-files).
- A loader the build of `zibri/webpack` uses, such as `ts-loader` or `css-loader`, that the application has not installed fails the build before it starts, naming the package to install.
- **An application without logins.** `authStrategies: []` registers no auth strategy, and no authenticator or two factor method unless the application names them, so an API open to everyone needs none of their configuration. A route that needs a login then stops the start, naming the route. An empty list was taken for a list left out, and given the default. `authenticators: []` and `twoFactorMethods: []` register none of theirs as well. See [registering strategies and authenticators](https://service-soft.github.io/zibri/auth/auth/#registering-strategies-and-authenticators).
- **`HttpClientBufferedBody`** sends bytes held as the chunks they were read in, such as one part of a large upload, with their `content-length` and without joining them into one buffer first. Every attempt and every redirect sends it whole again. See [setting the request body](https://service-soft.github.io/zibri/endpoints/http-client/#setting-request-body-query-and-header-params).
- **`validateRedirect`** of a request checks every redirect it follows, handed the URL it leads to, and fails the request when it throws, so that the address a redirect of a URL your users give you leads to is checked as the first one was. See [following redirects](https://service-soft.github.io/zibri/endpoints/http-client/#following-redirects).
- **Version 2 of backup transports.** `BackupTransportInterface` takes the versions a transport supports: `BackupTransportInterface<'v2'>` opens sessions that put, get, list and delete data under keys, knowing nothing of backups, and names `versions: ['v2']`. One session serves everything one resource of a backup or a restore does. `BackupTransportInterface` without a version is a transport of `v1`, as in 3.0, and one supporting both, `BackupTransportInterface<'v1' | 'v2'>`, is used as `v2`. The new `FsBackupTransport`, `S3BackupTransport` and `SftpBackupTransport` are built with a name and their options, and support both versions, as `BaseBackupTransport`, which they extend, does for any transport implementing `openSession`. Every backup keeps its keys, so what the transports stored before is found and restored where it is. A put is whole or nothing: the fs and SFTP transports write a resource into the folder `.partial` and rename it into place, as SFTP did the record alone, and the next backup deletes what an interrupted one left there after a day. A folder the application may not read, such as a disk's `lost+found`, is skipped with a warning when backups are synced, and `get` of a session fails with `BackupKeyAccessDeniedError` for it. The S3 transport deletes up to 1,000 objects in one request. The fs transport refuses a file larger than the size its backup recorded, as the others did. See [writing a transport of your own](https://service-soft.github.io/zibri/data/backup/#writing-a-transport-of-your-own).
- **Backups store unchanged data once.** A backup cuts each resource into chunks of about 1 MiB at boundaries its content decides, compresses each with zstd and, with `encrypt`, encrypts it under the repository key of the application, which each transport holds encrypted by the master key. A transport keeps each chunk once, so a backup stores the chunks no earlier backup stored: of a table only ever added to, what was added. 100 MB of rows took about 30 MiB per backup on a transport instead of 100 MB. Backups are written in format 2, under `.zibri-repository/` of each transport, and backups of format 1 are found and restored where they are. `BackupChunkEntity` records which chunks each transport holds: declare it beside `BackupEntity`, which with `schemaManagement: 'migrations'` takes a migration. Without it, each backup lists the chunks its transports hold first, and the application warns at boot. `ZIBRI_DI_TOKENS.BACKUP_CHUNKING_OPTIONS` sets the sizes of the chunks and the level. A blob store of your own implements `findNames` of a session as well, and no backup may be named `.zibri-repository`. `createBackupData` of a resource is handed `BackupDataOptions`, whose `chunked` says the backup cuts the data into chunks: a resource that compresses its data leaves that off then, since compressed data is not stored once. A Postgres data source dumps uncompressed then. Every file a backup or a restore stages in `BACKUP_TEMP_FOLDER` is compressed with zstd, and of a resource with `encrypt`, encrypted: what a backup stages and the snapshot of what the resource held under a key of their own, which the journal keeps encrypted by the master key for a snapshot, and the chunks a restore fetched as they were stored, under the repository key. A Valkey data source writes its keys in the order of their names, sorted in the `stagingFolder` of the options, encrypted, so that keys that did not change are stored once. See [storing unchanged data once](https://service-soft.github.io/zibri/data/backup/#storing-unchanged-data-once).
- **The space of deleted backups comes back.** `BackupGarbageCollectionCronJob`, registered for you, deletes once a day what the backup transports hold that no backup needs: the chunks only deleted backups named, and what backups that never finished stored. While it deletes, a resource waits a few seconds at a time to be stored, and a restore goes on. It forgets a chunk recorded as stored that a transport does not hold, so the next backup stores it again, and logs every backup naming one as an error. `collectGarbage` of `BackupServiceInterface` runs it at once, which is optional until 4.0 for a backup service of your own. With `ZIBRI_DI_TOKENS.BACKUP_SCRUB_OPTIONS`, it also reads the stored chunks back over `cycleInDays` and checks each, deleting one that changed. See [freeing the space of deleted backups](https://service-soft.github.io/zibri/data/backup/#freeing-the-space-of-deleted-backups).
- **Backups read only what changed.** A Postgres data source with `incrementalRead: true` reads only the rows that changed since the backup before, through logical decoding, written through a repository or not, rather than dumping everything each time. A restore applies the backup in full it builds on and every backup after it, in one transaction. The first backup of each week reads in full, or of each period `fullRead` of `BackupRetention` names, as does the next one after a restore or a change of the schema. A backup starts once the transactions writing when it began have ended, and warns every 10 seconds while one is open, naming it. The retention keeps every backup a kept one builds on, and `delete` refuses a backup another one builds on with a `409`. The data source checks at boot what the server and the role backups run as need: `wal_level` `logical`, `max_slot_wal_keep_size` set, two free replication slots, a database encoded in `UTF8`, and a role allowed to replicate and to set `session_replication_role`, with `CREATE` on the database and owning the tables read through the changes. `BackupResourceEntity` records the backup it builds on and where the next one reads on from. A resource of your own reads only what changed by implementing `IncrementalBackupResourceInterface`. The Postgres container of `zibri-testing` runs with `wal_level` `logical`, and grants the role what `incrementalRead` needs when the data source sets it. See [reading only what changed](https://service-soft.github.io/zibri/data/backup/#reading-only-what-changed).
- **Backups of a tenant.** `queueBackup({ tenantId })` backs up the rows of one tenant, as they are stored and as of one moment, in every data source marked with `@Backup` that holds rows of tenants, to the tenant's own transports, and `restore` of it replaces exactly the tenant's rows in each data source in one transaction while every other tenant goes on working. Shared rows are never touched, and the rows of append-only and chained entities stay as they are. A row such a row points at is written over in place, and kept when it was created since, soft deleted where its entity soft deletes; a value of a unique it holds that the backup gives to another row gives way to a stand-in, such as `<value>_<moment of the restore>` for a text, and a warning names the kept rows. `restoreBackup` of `BackupResourceInterface` gets a function reading the data again. The restore is recorded in the tenant's audit trail as `backup.tenant.restored`, and the retention counts each tenant's backups apart from the application's. `BackupEntity` records the tenant. See [backing up a tenant](https://service-soft.github.io/zibri/data/backup/#backing-up-a-tenant).
- **Exporting a tenant.** `exportTenant` of `BackupServiceInterface` writes the rows of a tenant as the application answers them, readable without it: a tar archive of a manifest and a folder per data source holding a file per entity, in JSON lines or CSV. In CSV, text a spreadsheet would run as a formula starts with a `'`. Encrypted values are decrypted, hashed and excluded properties left out. It is optional until 4.0 for a backup service of your own. See [exporting a tenant](https://service-soft.github.io/zibri/data/backup/#exporting-a-tenant).
- **A tenant's own storage for its backups.** With `TenantBackupTransport` declared, `createTenantBackupTransport` adds storage a tenant keeps its backups on, of a kind the application lists: a bucket over https, `S3TenantBackupTransportKind`, an SFTP server, `SftpTenantBackupTransportKind`, or a kind of your own implementing `TenantBackupTransportKindInterface`, whose settings and secret are checked against the models it names and whose every host is checked through the `TenantTransportNetwork` it is handed. Its secret is encrypted and bound to the row, written to and deleted from once so that a wrong one is refused at once. A tenant's backups go there alone, encrypted with a repository key of the tenant's own, and a backup of a tenant without one is refused; the garbage collection goes through them too, and records the backups they hold that the database does not, such as after it was restored, as does one instance as the application starts for the transports no recorded backup names. `syncTenantBackupEntities` records those of one tenant at once. A host leading to this machine or a private network is refused when it is added and before every session, and so is a redirect a bucket answers with and a bucket name that is no name of a bucket; `ZIBRI_DI_TOKENS.BACKUP_TENANT_TRANSPORT_OPTIONS` narrows the kinds and hosts, or with `allowPrivateNetworks` lets tenants reach inside. With `TenantBackupSettings` declared, `setTenantBackupRetention` keeps a tenant's backups by a retention of its own. The methods are optional until 4.0 for a backup service of your own. See [letting a tenant back up to its own storage](https://service-soft.github.io/zibri/data/backup/#letting-a-tenant-back-up-to-its-own-storage).
- **`REPEATABLE READ` on Valkey.** A transaction of a `ValKeyDataSource` started with `REPEATABLE READ` reads every row as it was at its first read: each write through the data source meanwhile copies the row it writes first, which the transaction reads, and the server holds those copies until it ends. Its commit fails with a `TransactionSerializationError` when another transaction wrote a row it writes since. `SERIALIZABLE` runs as `REPEATABLE READ` with a warning, and `READ COMMITTED` no longer warns. Both levels were ignored with a warning. See [differences to a SQL data source](https://service-soft.github.io/zibri/data/data-source/#differences-to-a-sql-data-source).
- **A Valkey restore in place.** A `ValKeyDataSource` marked with `@Backup` sets `restoreMode`. `'staged'` writes the backup beside what is stored and swaps it in at one moment, as every restore did: the server holds both until then, and answers nothing else while it swaps. `'direct'` deletes what is stored and writes the backup in its place a batch at a time, while the server goes on answering: it needs no memory beyond what the backup holds, a reader meanwhile sees part of the backup, and a restore that fails part way is put back from its snapshot. A restore of a tenant follows it: `'direct'` replaces the tenant's rows a batch at a time rather than in one transaction, which holds every row in the application until it commits. Without `restoreMode`, the application warns at boot and restores `'staged'`. See [backing up a data source](https://service-soft.github.io/zibri/data/backup/#backing-up-a-data-source).
- **A restore is told whether there is room for it before it starts.** Each backup records of each resource what it took as staged, `stagedSize` of `BackupResourceEntity`. Once a backup is completed, the instance that completed it logs a critical error when its disk could not restore it. A restore checks the disk of `BACKUP_TEMP_FOLDER` before it fetches anything, and again before it takes the copies it puts back from, and is refused with a `NotEnoughRestoreSpaceError` that names what each resource takes, what is free, and every way to go on with what each gives up. A disk that runs out while a restore fetches or copies ends it with the same error before anything changed, and is no longer tried on the next transport. A Postgres server that runs out of disk replacing the tables, and a Valkey server that runs out of memory staging a backup, fail the restore saying what they hold, what replacing it takes and what to do. `restore` takes `RestoreOptions`: `resources` restores the named resources alone, `putBack: false` keeps no copies, `deleteFirst` deletes what each data source holds before the backup is applied, which a resource of your own implements with `deleteBackedUpData` of `BackupResourceInterface`, and `skipSpaceCheck` goes on regardless. See [sizing the server for backups and restores](https://service-soft.github.io/zibri/data/backup/#sizing-the-server-for-backups-and-restores) and [restoring with less room](https://service-soft.github.io/zibri/data/backup/#restoring-with-less-room).
- **A restore of one data source needs half the disk.** A restore of a single resource whose restore changes everything or nothing by itself keeps no copy of the current data to put back. A Postgres data source restores so when the backup records exactly the migrations of the build, read from the dump before anything is applied, and no backup after the one in full it builds on records a migration, a Valkey data source with `restoreMode: 'staged'` when its backup does, and a backup of a tenant does, except on a Valkey data source with `restoreMode: 'direct'`. A resource of your own says so with `resolveRestoresWhole` of `BackupResourceInterface`. See [a restore of several resources](https://service-soft.github.io/zibri/data/backup/#a-restore-of-several-resources).
- `resolveApplicationPackage` loads a package a plugin leaves to the application, failing with the feature it was needed for and the command that installs it.
- **Commands of your own.** `commands` of the application options lists `AppCommand`s, which `runCommand` runs in place of starting, named by the first argument, such as `node dist/bundle.js deactivate-user ada@example.com`. An application with commands warns about a first argument that names none of them, listing them, and starts. From 4.0 it refuses one. See [commands](https://service-soft.github.io/zibri/application/commands/).
- **Logging everybody out.** `endEveryLogin` of `AuthServiceInterface` ends every login of every user, in every strategy, recorded as `auth.every-login.ended`. A login strategy of your own implements `endEveryLogin` of `LoginAuthStrategyInterface`, which is optional until 4.0. So are `endEveryLogin` and `setPassword` on `AuthServiceInterface`, for an auth service of your own. See [logging everybody out](https://service-soft.github.io/zibri/auth/auth/#logging-everybody-out).
- **The code that enrolls a one time password finishes the login too.** A user enrolling their first second factor at login presents the same code at `POST /login/2fa/confirm`, rather than waiting for the authenticator to show the next one. See [asking for a second factor at login](https://service-soft.github.io/zibri/auth/two-factor/#asking-for-a-second-factor-at-login).
- **One route for every email link.** `POST /confirm-email` of the `AuthController`, there with `confirmEmailRoute: true` beside `emailVerification` in its options, confirms a link of either purpose, as `confirm-email-verification` and `confirm-email-change` do, and answers an `EmailConfirmation`: what the link was for and whether that is done. The links look alike, so the page they open couldn't tell which route to call. `confirmEmail` of `EmailVerificationServiceInterface` does it, which is optional until 4.0 for a service of your own, and an application asking for the route with a service without it refuses to start. See [verifying email addresses](https://service-soft.github.io/zibri/auth/email-verification/#setting-it-up).
- **The previous address approves a change.** With `previousAddressConfirms` of `EMAIL_VERIFICATION_OPTIONS`, a change of an address mails a link to the previous address as well, and takes effect once both links were followed, in either order. Off by default. The template of `verificationEmail` is given the `purpose` `change-approval` for it, and `EmailVerificationToken` stores the links of a change that were followed. `EmailVerificationPurpose` gains `'change-approval'` for it: a template that switches over every `purpose` needs a case for it to compile, which it is only ever given with `previousAddressConfirms`. See [changing an address](https://service-soft.github.io/zibri/auth/email-verification/#changing-an-address).
- **Setting a password for a user.** `setPassword` of `AuthServiceInterface` sets a password without the one the user has, lifts a lock of wrong passwords, ends their logins and is recorded as `auth.password.set`. With `requireChange` the user chooses their own at their next login. See [setting a password for a user](https://service-soft.github.io/zibri/auth/auth/#setting-a-password-for-a-user).
- **`GET /me`** of the `AuthController`, there with `currentUserRoute: true` in its options, answers the logged in user as a `CurrentUserProfile`: their id and email, when they verified it, their `platformPermissions`, and their active `memberships`, each a `CurrentUserMembership` with the `permissions` of its tenant, so a frontend shows only what the user may do and switches tenants without asking again. `resolveCurrentMemberships` of `AuthServiceInterface` resolves them, which is optional until 4.0 for an auth service of your own. See [checking permissions in a frontend](https://service-soft.github.io/zibri/auth/roles-and-permissions/#checking-permissions-in-a-frontend).
- **`GET /2fa/registrations`** of the `AuthController`, there with `twoFactorRegistrationsRoute: true` in its options, answers the two factor methods the logged in user has enrolled, as `TwoFactorRegistrations`. See [enrolling a user](https://service-soft.github.io/zibri/auth/two-factor/#enrolling-a-user).
- A route guarded by `@Auth.require2fa` called without a second factor answers `401` with the name `SecondFactorMissingError`, so a frontend asks its user for a code instead of refreshing the login. A two factor method of your own throws it when its header is missing. See [what a second factor is for](https://service-soft.github.io/zibri/auth/two-factor/#what-a-second-factor-is-for).
- `ErrorResponseBody`, the JSON body an error is answered with, is exported.
- **A wait that goes on says what it waits for.** A lease taken with `mode: 'wait'` warns every 30 seconds while somebody else holds it, naming the key, the instance holding it and until when, and `waitForBackup` warns where the backup stands: each resource stored or not, its failed attempts, when the next is due and what the last failed with. A `PostgresDataSource` reading its data for a backup or for the copy a restore keeps warns where the read stands: the step it is at, whether it waits for the backup to read on, and what each busy connection to the database waits for, naming the connections holding a lock one waits for. A query it names is logged with each string in it as `'*****'`. `ZIBRI_DI_TOKENS.WAIT_REPORT_INTERVAL_IN_MS` sets how often. See [choosing how a lease is acquired](https://service-soft.github.io/zibri/data/leases/#choosing-how-it-is-acquired-and-released).

### Generating and upgrading a project
- A build for an editor, `npm start` included, is cached in `node_modules/.cache/webpack`, so the next one compiles only what changed: a project generated with every feature builds in about 4 seconds instead of 13 the second time. The cache starts over when the build, the compiler of the templates or `zibri-mdx` changes. A build for a deployment, `--env deployment`, caches nothing, so the image stays as large as it is. See [the generated project](https://service-soft.github.io/zibri/application/project-layout/).
- The compiler of the templates compiles a template in about half the time, which shows most on pages written in markdown.

### Fixed
- **The stack trace of a logged error is only in its `stackTrace`.** `errorToLoggedError` put it into the `paragraphs` as well, so an email of a log, or a log history that shows both, showed it twice. `stackTrace` now holds the stacks of the causes too, after the one of the error, and the console prints it after the paragraphs as before.
- **A stream of more than 500 rows in a Postgres transaction waited forever.** It reads the rows back a batch at a time, and in a transaction the read of a batch queued behind the stream on the transaction's one connection. It reads through a cursor declared in the transaction now, which leaves the connection free between batches, so whatever the reader runs in the transaction goes on as well.
- **Deleting rows that other rows point at read the pointing table once for every row deleted, on Postgres.** Postgres indexes the key a foreign key refers to and not the column holding it, so deleting many rows pointed at from a large table ran into the statement timeout, as a restore of a tenant deleting its change sets did. The column of every `manyToOne` and `belongsToOne` is indexed now, unless an index or unique the entity declares starts with it, and `ChangeSet` is indexed by the row it describes. The indexes are built once the first instance of 3.1 started, which waits for none of them. An instance of 3.0 started beside it leaves them alone.
- **A Postgres connection ended by the server while it was in use ended the process.** A connection taken out of the pool had no listener for its failure, so a restart of the database, or a connection terminated by an administrator, between two statements of whoever held it, crashed the application. It is logged now, and whoever holds the connection learns from its next statement failing.
- **What was encrypted after a restore of the application could be unreadable after the next start.** The restore brought back the data keys as the backup held them, while every instance running went on encrypting with the key it had read before, which the backup lacked after restoring onto a fresh database or after a key rotation since the backup. A restore keeps the data keys and signing keys stored when it began beside those of the backup, the default ones staying the default, and the next start writes them back when the restore was killed before it did. An encryption service of your own implements `resolveKeptKeys` and `putBackKeptKeys`, optional until 4.0. See [encrypting backups](https://service-soft.github.io/zibri/data/backup/#encrypting-backups).
- The first requests after a restart of a Postgres server could answer `500`: a connection the server ended tells its client a moment later, and a statement taking it before then failed, and gave the connection back to the pool. A statement outside a transaction whose connection the server ended before it committed, `57P01`, `57P02` or `57P03`, or that failed before it was sent, runs again on the next connection, and the ended one is closed. One that may have committed, on a connection that ended without saying why, fails as it did. See [when the database cannot be reached](https://service-soft.github.io/zibri/operations/incidents/#when-the-database-cannot-be-reached).
- An instance applied a cache invalidation it published itself a second time at its next poll, emptying what was cached since a couple of seconds after the first time. It applies its own once, as it publishes it.
- **After a restore, every instance went on answering from what it held in memory before.** A restore replaced the rows without invalidating any tag, so the caches answered with what the restore had replaced until their entries expired, and a restore of the application left the roles as they were, so a permission taken from a role since the backup was still granted until the next start. Once a restore is done or put back, every cache is emptied after one of the application, and after one of a tenant, what was cached for the tenant and outside every tenant, on every instance. Every entry carries the tag of the tenant it was written for, and `CacheRestoreTagUtilities` names the tags, which a listener of `registerInvalidationListener` keeping rows in memory listens for. A cache store of your own keying by `cacheKeyOf(key, false)` sets `perTenant: false` in its `config`. See [restoring a backup](https://service-soft.github.io/zibri/data/caching/#restoring-a-backup).
- **For up to 20 seconds after a restore of the application, an event did not reach the subscribers of other instances.** The restore brought back the registrations of the subscribers as the backup held them, lapsed or missing those added since, so an event emitted before each instance renewed its own owed them no run, and one the backup held unfinished was settled without them. `EventSubscriberRegistration` is declared `backedUp: false`, and a restore keeps the registrations of the instances running. Other instances keep running while a restore runs, see [restoring while other instances run](https://service-soft.github.io/zibri/data/backup/#restoring-while-other-instances-run).
- **A restore of the application brought back the logins and credentials of the backup's moment.** A login ended since the backup worked again, and one started since was gone; a password changed since stopped working while the one before worked again, and an api key, passkey or second factor revoked since was back while one created since was gone. The logins, what a login under way holds and the counts of failed attempts and rate limits are declared `backedUp: false`, and a restore keeps them as they are. The credentials are declared `backedUp: 'keptForCurrentUsers'`, a new value of `backedUp`: a restore keeps those of every user that exists when it begins, and those of the backup come back for the users that did not exist then, such as on a fresh database. `OAuthProviderTokens` is declared `backedUp: { keptWith: () => FederatedIdentity, by: 'identityId' }`, another new value: a restore keeps a row exactly when it keeps the row it names. The next start writes them back when the restore was killed before it did. A user service of your own implements `streamUserIds` and `findStoredUserIds` of `UserServiceInterface`, optional until 4.0. See [keeping rows across a restore](https://service-soft.github.io/zibri/data/backup/#keeping-rows-across-a-restore).
- **After a restore of the application, a reconnecting websocket client missed the messages sent since.** The restore set the seq of the messages back, so the next messages were given seqs the client already had, and a replay after its `offset` left them out until the seqs passed it. A client whose `offset` is past the newest message is sent `ws:replay-incomplete`, and reloads. See [reconnecting](https://service-soft.github.io/zibri/endpoints/websocket/#reconnecting).
- **A restore held the data of an encrypted resource unencrypted on the instance's disk.** What it fetched, and the snapshot of what each resource held, were written as they were, while the documentation said the disk never holds that data unencrypted. Both are encrypted now, as the staged copy of a backup is. See [a restore of several resources](https://service-soft.github.io/zibri/data/backup/#a-restore-of-several-resources).

The next start puts it back, the way it puts back a killed restore, and every restore on the instance is refused with a `409` until then. See [a restore of several resources](https://service-soft.github.io/zibri/data/backup/#a-restore-of-several-resources).

See [setting the master key](https://service-soft.github.io/zibri/data/encryption-and-hashing/#setting-the-master-key).
- Validation messages say what a value needs to be, such as `needs to be of type string` and `A password needs to be at least 15 characters long.`, where they stated it as a fact. Translations of these messages are keyed by their new text.
- Every install of a project `zi new` generated warned that `glob@10` is deprecated, which jest's coverage installs through `test-exclude` 7. The generated `package.json` overrides `test-exclude` with version 8, the same code on a newer glob. A project generated before adds `"overrides": { "test-exclude": "^8.0.0" }` to its `package.json` for the same.
- Every install of a project `zi new` generated reported two moderate advisories in what jest installs: glob 13 ([GHSA-3g3m-2fjr-6pw4](https://github.com/advisories/GHSA-3g3m-2fjr-6pw4)) and minimatch 10 ([GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249)). The generated `package.json` overrides glob 13 with 14.0.2, which brings a fixed minimatch, and the minimatch of `test-exclude` with 11.0.1. A project generated before replaces `"test-exclude": "^8.0.0"` in its `overrides` with `"glob@^13.0.0": "^14.0.2"` and `"test-exclude": { ".": "^8.0.0", "minimatch": "^11.0.1" }` for the same. minimatch 11 has no `makeRe`, so an override of every minimatch 10 breaks packages calling it, such as eslint's plugins.
- Every install of a project `zi new` generated warned, from npm 11.19 on, that the install scripts of `re2` and `@parcel/watcher` are not covered by `allowScripts`. The generated `package.json` allows the one of `re2`, so it keeps its native module once npm stops running scripts it was not told of, and denies the one of `@parcel/watcher`, which builds only when told to build from source. A project generated before adds `"allowScripts": { "re2": true, "@parcel/watcher": false }` to its `package.json` for the same.

## 3.0.0

A major release. An application on 2.x needs changes before it starts on 3.0.0, and its database needs a migration. [Upgrading to 3](https://service-soft.github.io/zibri/releases/upgrading-to-3/) lists both: what the compiler does not tell you about, and the migration for the tables Zibri ships. Back up your database first.

Zibri 3 needs node 24 or newer.

### New packages
- **`zibri-tsx`** compiles the `.tsx` templates of pages and emails at build time, in place of preact. A component can carry code that runs in the browser. See [templating](https://service-soft.github.io/zibri/templates/templating/).
- **`zibri-testing`** starts your application in a test with the router, auth, lifecycle and error handling production has. Its in-memory data source needs no database, and it starts Postgres and Valkey containers or a cluster of instances when a test asks for them. See [testing](https://service-soft.github.io/zibri/testing/).
- **`zibri/internal`** is a second entry point of `zibri`, for what only a data source, driver, parser or router of your own needs. See [releases](https://service-soft.github.io/zibri/releases/releases/#what-is-public).

### Generating and upgrading a project
- `zi new` writes a project that builds, tests and runs as it stands, with a Dockerfile, a CI workflow and its configuration read from the environment. Pages, mailing lists, a metrics dashboard and a log email are features you choose.
- `zi add` and `zi remove` add or remove a feature later.
- `zi upgrade` merges what a new release generates into your project, the way git merges a branch.
- `zi migrate` creates a migration from what your entities changed, and records a baseline.
- The build, the jest configuration and the compiler options come from the packages: `zibri/webpack`, the `zibri-testing` preset and `zibri/tsconfig.application.json`. Updating the packages updates them.
- A deployed image names the source file and line in every stack trace.

See [getting started](https://service-soft.github.io/zibri/getting-started/) and [the generated project](https://service-soft.github.io/zibri/application/project-layout/).

### Data
- **Postgres without TypeORM.** The Postgres data source talks to `pg` itself and builds its queries itself. How the schema is managed, TLS and the pooler in front of the database are options you set. See [data sources](https://service-soft.github.io/zibri/data/data-source/).
- **Valkey data source**, with the same repositories as Postgres.
- **Tenants.** Every row belongs to a tenant or is shared, and every read and write stays inside the tenant of the request. See [tenants](https://service-soft.github.io/zibri/data/tenancy/).
- **Transactions across data sources**, and a `TransactionConflictError` for a deadlock or a serialization failure.
- **Tamper-evident tables.** Append-only entities, and chained entities whose rows form a hash chain. See [tamper-evident tables](https://service-soft.github.io/zibri/data/tamper-evident-tables/).
- **What a call costs.** Every repository call has a documented number of round trips. See [costs](https://service-soft.github.io/zibri/data/costs/).

### Logging in
- **Single sign-on** through OpenID Connect (Google, Apple, Microsoft Entra ID, Keycloak), plain OAuth2 (GitHub) and SAML 2.0. See [login through a provider](https://service-soft.github.io/zibri/auth/login-through-a-provider/).
- **Directory login** against LDAP, such as Active Directory. See [login through a directory](https://service-soft.github.io/zibri/auth/login-through-a-directory/).
- **Passkeys**, to log in and as a second factor, and recovery codes beside TOTP. See [passkeys](https://service-soft.github.io/zibri/auth/passkeys/) and [two factor](https://service-soft.github.io/zibri/auth/two-factor/).
- **Services calling your API** with [API keys](https://service-soft.github.io/zibri/auth/api-keys/), [client certificates](https://service-soft.github.io/zibri/auth/client-certificates/), [tokens your application issues](https://service-soft.github.io/zibri/auth/authorization-server/) or [tokens of your identity provider](https://service-soft.github.io/zibri/auth/provider-tokens/). Tokens can be bound to a key with [DPoP](https://service-soft.github.io/zibri/auth/dpop/).
- **Roles and permissions.** Roles are rows, permissions are declared in code, at the tenant or the platform level, with wildcards. See [roles and permissions](https://service-soft.github.io/zibri/auth/roles-and-permissions/).
- **SCIM provisioning** from a tenant's identity provider. See [SCIM](https://service-soft.github.io/zibri/auth/scim/).
- **Email verification**, a required password policy, scrypt as the default hash, and an optional lock after too many wrong passwords. See [verifying email addresses](https://service-soft.github.io/zibri/auth/email-verification/) and [auth](https://service-soft.github.io/zibri/auth/auth/).
- **`AuthController`** defines the auth routes. See [the auth routes](https://service-soft.github.io/zibri/auth/auth-routes/).
- **Audit trail.** Logins, refused routes, password resets and role changes are recorded in a tamper-evident trail. See [audit trail](https://service-soft.github.io/zibri/data/audit/).

### Running in production
- **Several instances.** Cron jobs, events, mails and named locks are claimed through [leases](https://service-soft.github.io/zibri/data/leases/), so every instance is equal. See [replication](https://service-soft.github.io/zibri/data/replication/).
- **Tracing** through OpenTelemetry, and metrics labeled by route. See [tracing](https://service-soft.github.io/zibri/operations/tracing/) and [metrics](https://service-soft.github.io/zibri/operations/metrics/).
- **Backups** to S3 and SFTP beside a folder, encrypted, and key rotation for encrypted properties. See [backup](https://service-soft.github.io/zibri/data/backup/) and [encryption and hashing](https://service-soft.github.io/zibri/data/encryption-and-hashing/#rotating-a-key).
- **Limits on requests and statements**, and an HTTP client that stops calling an upstream that keeps failing.
- **XML** request and response bodies, validated against a model like JSON. See [XML](https://service-soft.github.io/zibri/endpoints/xml/).
- **Recovering failed work.** A failed cron job, event, thread job, mail or backup keeps what it failed with, and can be started again. See [recovering work that stopped](https://service-soft.github.io/zibri/background-work/troubleshooting/).

### Packages you install
Zibri installs only what every application needs. The package of each feature, such as `pg`, `nodemailer` or `socket.io`, is installed by the application that uses it, and the application names a missing one while it starts. See the respective Requirements section of each feature.
